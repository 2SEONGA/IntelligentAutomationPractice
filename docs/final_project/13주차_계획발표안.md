# 13주차 기말 팀 프로젝트 계획 발표안

## 발표 개요

- **제목:** RAG + LangGraph 기반 공공 SI 입찰 핵심정보 검증 Agent
- **부제:** 근거가 확인된 정보만 입찰 분석으로 전달하는 T1.5 검증 흐름
- **발표 시간:** 약 10분, 12장 (2026-11-18 구현 진행 M1–M31 반영: 9장 수정, 10·11장 추가)
- **데이터 수준:** Level A — 실제 데이터 중심
- **프로젝트 범위:** 입찰 검토 전체 업무에서 금액·참가자격·기간의 원문 정보 검증을 핵심 개선 문제로 선정

## 1장 — 주제와 한 문장 문제 정의 (0:35)

### 화면 문구

**공공 SI 입찰 검토에서 핵심정보가 잘못 추출되면, 그 오류가 입찰 판단까지 이어질 수 있습니다.**

RFP·공고문에서 사업금액·참가자격·기간을 추출하고, 원문 근거로 검증한 뒤 불확실하면 추가 검색 또는 담당자에게 전달합니다.

### 발표 메모

3~5주차 CrewAI 프로젝트에서 공공 SI 입찰 검토 시스템을 만들었습니다. 이번 기말에는 기존 분석을 더 늘리는 대신, 후속 분석에 앞서 핵심정보의 정확성과 완전성을 확인하는 T1.5 검증 단계를 추가합니다.

## 4장 — 제안 시스템과 T1.5 검증 단계 (0:50)

### 화면 문구

`공고/RFP → T1 추출 → T1.5 근거 검증 → T2 역량 매칭 + T3 시장 조사 → T4 보고서 → 사람 최종 결정`

검증 상태:

- **확인됨:** 근거와 추출 정보 일치
- **추가 검색:** 관련 원문 구간을 더 탐색
- **충돌/담당자 확인:** 자동으로 확정하지 않고 근거와 질문 전달

### 발표 메모

T1.5 검증은 전체 검토의 병목이 아니라 잘못된 정보 전파를 막는 게이트입니다. 통과한 정보는 기존 분석으로 전달하고, 통과하지 못한 정보는 이유와 출처를 유지합니다. 최종 Go/No-Go는 계속 사람이 결정합니다.

### 화면 문구

- **원본 RFP 3건:** 사용자가 원본 PDF임을 확인
- **나라장터 공고 데이터:** 실제 공고·첨부 링크 및 낙찰정보
- **회사 공개 근거:** 공식 웹사이트·한국거래소 공시를 연결한 사전 검토 자료
- **Level A:** 실제 공개자료 중심

데이터의 역할과 한계는 구분합니다. 낙찰 기록은 수주 패턴이지 내부 Go/No-Go 정답은 아닙니다.

### 발표 메모

나라장터 낙찰자료에는 2023년 10월부터 2026년 10월까지 조회한 용역 351,025건과 그룹 낙찰 93건이 기록돼 있습니다. RFP에는 연락처 등 개인정보가 있을 수 있어 색인·발표 화면에서는 불필요한 값을 가립니다. 기존 AI 보고서를 사실 근거 코퍼스에 섞지 않습니다.

### 출처 표기

나라장터 입찰공고/낙찰정보 API, `data/input/` 원본 RFP, `data/company/company`에 기록된 ITCEN ENTEC·KIND 공개 출처.

## 6장 — RAG 계획: 검색한 근거가 검증에 쓰이는 방식 (0:55)

### 화면 문구

**검색 입력:** T1 주장 + 정보 유형 + 공고번호/판본  
**검색 대상:** 원본 RFP·공고문·정정/재공고 첨부  
**검색 결과:** 문서·판본·페이지·조항·인용문  
**업무 활용:** T1.5가 원문과 대조하고 근거가 부족하면 재검색

문서 분할은 조항·문단·표 행을 기준으로 하며 페이지와 표 맥락을 보존합니다.

### 발표 메모

금액이면 예산·추정가격·VAT·연차별 금액 표현을, 자격이면 등록·공동수급·제한·예외 조항을, 기간이면 수행기간과 각 제출 마감일을 검색합니다. CDW 자료는 재공고 첨부가 수정 문서로 표시돼 있어 판본을 구분합니다. 검색 결과가 없다는 사실만으로 문서에 해당 조건이 없다고 판단하지 않습니다.

### 화면 문구

| 범주 | 교차 확인할 핵심 요소 | 미해결 시 |
|---|---|---|
| 금액 | 유형·총액/연차·VAT·단위 변환·문서 간 차이 | 재검색 또는 담당자 확인 |
| 참가자격 | 적용 주체·등록/실적·제한·공동수급·예외·전체 구간 누락 | 해당 조항 재탐색 또는 담당자/법무 확인 |
| 기간 | 수행기간·시작 기준·제안/입찰/공동수급 마감·날짜 충돌 | 판본/표 문맥 재검색 또는 담당자 확인 |

각 범주에 독립 상태·근거·누락/충돌 시나리오를 둡니다.

### 발표 메모

단순히 세 항목에 하나의 정확도 점수를 붙이지 않습니다. 각 범주별로 필요한 정보와 완전성 확인 방법이 다릅니다. 특히 참가자격은 전체 관련 섹션을 탐색해 조건과 예외를 모두 기록해야 합니다. T1.5는 문서의 조건을 확인하고, 회사 충족 여부는 T2가 다룹니다.

## 8장 — LangGraph State와 조건 분기 (1:05)

### 화면 문구

```text
문서 준비 → T1 추출 → 금액/자격/기간 검증
                         ↓
           충분한 근거인가?
          ↙              ↘
    추가 검색            충돌/불확실
       ↓                    ↓
    재검증             Human Review
       └──── 확인됨 ────────┘
                         ↓
                  T2/T3 → 보고서
```

State: 입력문서·판본, 추출 주장, 범주별 근거/검증결과, 재검색 횟수, 사람 확인 내용, 후속 분석 결과.

### 발표 메모

LangGraph가 검증 상태에 따라 검색을 반복하거나 멈추고, 사람이 응답하면 해당 항목부터 재개합니다. 범주별 재검색은 제한하고, 사람 응답이 없으면 자동 승인하지 않습니다. 이 반복·분기·중단·재개가 필요한 업무라 단순 순차 Chain만으로 관리하지 않습니다.

계획 때 세운 기술 선택 중 바뀐 것은 검색 계층 하나입니다. 색인 대상이 RFP·공고문 1,024 chunk 규모라 로컬 SQLite FTS5로 충분했고, 키워드로 못 찾을 때만 OpenAI 임베딩 의미 검색을 붙였습니다. LangGraph를 workflow owner로 두는 결정은 그대로 구현했습니다.

## 예상 질문과 답변

### 왜 RAG가 필요한가요?

검증은 추출값이 원문 어디에 어떻게 적혀 있는지를 확인해야 합니다. RAG가 관련 페이지·표·예외 조항을 찾아 인용과 함께 제공하므로 담당자가 원문을 다시 확인할 수 있습니다.

### 왜 LangGraph인가요?

정보가 충분하면 다음 분석으로 가고, 부족하면 재검색하며, 충돌·법률 해석이 필요하면 멈춰 사람에게 보내야 합니다. 사람 응답 후 해당 항목부터 재개하는 분기형 상태 관리가 필요합니다.

### 참가자격이 없다고 판단하면 되나요?

아닙니다. T1.5는 원문에 조건이 어떻게 적혔는지와 누락 여부를 확인합니다. 회사가 충족하는지는 T2가 회사 근거와 대조하고, 법적 적용과 최종 결정은 담당자/본부장이 확인합니다.

### 세 범위를 다 하면 얕아지지 않나요?

세 범주를 한 점수로 합치지 않고 각기 다른 필드·근거·예외·오류 사례를 둡니다. 구현도 범주별 기준을 먼저 완성한 뒤 통합합니다. 일정이 부족하면 주변 UI와 시연 사례 수를 줄이고 검증 기준은 낮추지 않습니다.

### 실제 데이터와 개인정보는 어떻게 다루나요?

원본 RFP와 공개 나라장터·회사자료를 사용합니다. 업무 판단에 필요하지 않은 담당자 연락처는 검색 인덱스·시연 화면에서 제외하거나 가리고 원본은 보존합니다.

### 기존 CrewAI는 왜 MVP에서 사용하지 않나요?

CrewAI는 선택 기술이고 LangGraph는 필수입니다. 두 오케스트레이터를 중첩하지 않고 LangGraph 한 곳에서 검색·검증·사람 검토를 제어합니다. 기존 데이터·도메인 코드·업무 규칙은 계속 재사용합니다.
