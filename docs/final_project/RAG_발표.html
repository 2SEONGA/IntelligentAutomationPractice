02
Why RAG

왜 RAG가 필요한가

기존 방식 (3~5주차)

T1(LLM)이 RFP에서 추출 → 바로 후속 분석

  • 사업금액·참가자격·기한이 틀려도 그대로 다음 단계로 전파
    4주차 테스트: 금액 오인식·누락, 참가자격 혼동
  • VAT 포함/별도, 예산 vs 추정가격, 입찰마감 vs 제안서 제출기한 구분이 섞임
  • 정답 문구를 프롬프트에 넣는 방식은 새 RFP에 쓸 수 없음
현재 방식

검증 단계 T1.5 + RAG

  • 추출값마다 원문에서 근거를 검색해 대조
  • 근거는 문서·페이지·인용문으로 보존 → 담당자가 바로 확인
  • 근거 부족·충돌이면 재검색 또는 사람 검토로 분기
RAG = "정답을 맞히는 검색"이 아니라 "확인할 근거를 가져오는 검색".
유사도만으로 정확성을 판정하지 않는다.

RAG ② Company Data

Agent 2: 요구사항별 회사 실적 후보 검색

  • 자료: ㈜아이티센엔텍 공개자료 11건 / 8개 출처 (별도 FTS5 색인)
  • 검색: 키워드 후보 + 의미 검색 후보를 합쳐 유사도 ≥ 0.35, 최대 3건
  • 잡음 제거: 보안서약·지식재산권·실적 인정 규칙 등 행정 조항은 검색 제외, 제외 사유 기록

  • 점수 미합산: 후보는 "확인할 증빙"이지 적합도 점수가 아님

Not Everything Needs RAG

공고 수집: RAG로 보완하려다 다른 방법을 택한 이유

① 문제 발견공고 수집이 공고명 키워드
5개에만 의존
→
② 처음 생각의미 검색(RAG)으로
놓친 공고를 보완
→
③ 먼저 측정"실제로 얼마나 놓치나?"
키워드 없는 전체 조회와 비교
→
④ 결정RAG 없이
전체 수집 + 기존 규칙 필터

측정 결과 (최근 30일, 나라장터 용역, 실제 API)

전체 조회키워드 5개
수집 공고17,449건1,094건
규칙 필터 통과92건38건
놓친 통과 공고54건 (59%)

놓친 예: 자치단체 공통기반 유지관리 269억(3년 연속 수주 사업의 후속), 한국지역정보개발원 8건, RISS·에듀넷 — 공고명이 "유지관리·운영"이라 키워드에 안 걸림

왜 RAG가 아닌가

  • 나라장터 API는 의미 검색이 안 됨 → RAG도 결국 먼저 넓게 받아야 함
  • 키워드 없는 전체 조회가 가능: 30일 약 2분 · API 약 20회
  • 분야 판정은 이미 조달분류 "ICT 서비스" 규칙이 담당 → 키워드 자체가 불필요
  • 키워드 추가는 끝이 없음 ("지능형 AX 고도화" 등 계속 누락)
보완 방식 (적용 완료) — 키워드 없이 전체 수집 → 금액·마감·조달분류·계약방법 규칙 필터 그대로 적용.
30일 17,453건을 76초에 수집 → 검토 대상 66 · 확인 필요 32. ICT 아닌 공고는 건수만 기록.
Agent 3 과거 RFP 수집도 같은 방식으로 전환 (후보 2,493 → 10,530건).

Principles & Limitations

RAG를 쓰면서 지킨 원칙과 남은 과제

지킨 원칙

  • 유사도는 판정이 아니라 단서 — 자격·실적·참여를 자동 확정하지 않음
  • 모든 근거에 문서·페이지·인용문 보존
  • 의미 검색 근거는 항상 담당자 검토로
  • 임베딩 API 실패 시 키워드 검색으로 폴백
  • 담당자 승인은 원 판정을 덮어쓰지 않고 감사 기록으로 별도 저장

남은 과제

  • 임계값(0.40 / 0.35 / 0.60)이 표본 기준 → 정답 라벨 평가셋으로 재조정
  • 추가 검색이 최상위 1건만 인용 → 긴 chunk 속 정답 줄이 밀림
  • 행정 조항 판별이 정규식 목록 → 새 서식에 취약
  • 회사 자료가 11건뿐 → 원본 증빙 확보 필요
  • 과거 RFP 재수집: 후보 10,530건 vs 첨부 API 하루 800회 → 수집 우선순위 결정 필요
정리 — RAG는 "답을 만드는 도구"가 아니라 "근거를 찾아 사람에게 보여주는 도구"로 사용했습니다.
① 핵심정보 검증 (1,024 chunk, 페이지 인용) · ② 회사 역량 후보 (잡음 46→32건) · ③ 과거 유사 사업 (진행 중)
공고 수집은 측정해 보니 RAG가 필요 없어 전체 수집 + 규칙 필터로 보완
