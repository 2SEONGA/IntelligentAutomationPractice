## 1. 무엇을 비교했나

T1.5 검증(또는 담당자 승인)이 끝난 뒤의 두 가지 실행 구조를 비교했다.

| 모드 | T1.5 이후 흐름 |
|---|---|
| 순차 (`sequential`, 기본값) | 회사 근거 검색 → T2 매칭 → T3 유사 사업 검색 → T2·T3 평가 → T4 |
| 병렬 (`parallel`) | 분기 → (회사 근거 검색 → T2 매칭) ‖ (T3 유사 사업 검색) → 둘 다 끝나면 T2·T3 평가 → T4 |

질문은 두 가지였다.
1. 병렬로 돌려도 **결과가 같은가?**
2. 같다면 **얼마나 빨라지는가?** 기본값을 바꿀 만큼인가?

## 2. 실측 방법

| 항목 | 내용 |
|---|---|
| 사례 | 5건: 상수도관(시연), CDW(시연), 과거 RFP 3건(전산장비 통합 유지보수 R26BK01648854, AI 디지털트윈 EV 정비 교육 콘텐츠 R26BK01758442, 온프레미스 멀티모달 AI·Graph RAG R26BK01765824) |
| 반복 | 사례마다 모드별 5회. 실행 순서를 회차마다 번갈아(순차→병렬, 병렬→순차) 캐시·네트워크 편향을 줄였다 |
| 워밍업 | 1회차는 시간 집계에서 제외 → 사례당 4쌍, 총 20쌍 |
| 담당자 승인 | 실제 공고는 대부분 T1.5에서 담당자 검토로 멈춘다. 두 모드에 같은 고정 승인(사유 "벤치마크용 고정 승인(실제 검토 판단 아님)", 검토자 `benchmark`)을 넣어 T2·T3까지 진행했다 |
| 고정 조건 | 회사 자료·검색 색인은 시험 중 바꾸지 않았다. 입력 파일 SHA-256을 기록하고 실행 전후로 대조했다 |
| 지표 | 전체 시간, **T1.5 이후 구간 시간**(전체에서 분기 전 Node 시간을 뺀 값 — 병렬화가 영향을 주는 구간), Node별 시간, 임베딩 토큰, 결과 동등성 |
| 판정 기준 (사전에 정함) | 모든 사례에서 결과가 같고 T1.5 이후 구간 중앙값이 20% 이상 줄면 병렬을 기본값 후보로 올린다. 아니면 순차 유지 |

명령:

```bash
PYTHONPATH=src python scripts/compare_workflow_modes.py \
  --cases <사례 JSON> --output outputs/workflow_compare/261120 \
  --repeats 5 --approve-note "벤치마크용 고정 승인(실제 검토 판단 아님)"
```

통합정보시스템은 원래 사례에 넣었지만, 승인 후에도 "공고 식별 충돌"로 멈춰 T2에 가지 못했다(6장 발견 1). 같은 방법으로 과거 RFP 1건(R26BK01765824)을 5회 추가 측정해 대체했다.

### 3.3 결과 동등성

- 판정, 적합도(%), T3 후보와 순서, T2·T3 평가 상태, T4 권고가 **모든 쌍에서 같았다.**
- 임베딩 토큰도 두 모드가 같았다(예: 상수도관 10,013토큰).
- 차이는 OpenAI 임베딩 점수의 소수 넷째 자리 흔들림뿐이었다(예: 0.4391 ↔ 0.4390). 같은 모드끼리 반복해도 생기는 차이라 모드 탓이 아니다.
- 한 가지 주의: CDW에서 점수가 회사 자료 임계값(0.36)에 정확히 걸린 후보 1건(`CAP-CERT-001`)이 5회 중 3회, 순차나 병렬 어느 한쪽에만 들어갔다. 어느 모드에 들어가는지는 회차마다 달랐다(3회차 순차, 4회차 병렬, 5회차 순차). 모드와 무관한 경계 잡음이며 적합도·판정은 바뀌지 않았다.

## 4. 해석

- **단축 폭은 이론값과 같다.** 병렬로 줄일 수 있는 최대치는 `min(T2, T3)`이다. 사례별 T2는 0.35~0.64초였고, 실제 단축 폭(0.25~0.87초)이 이 값과 거의 같다. 짧은 T2가 긴 T3와 겹친 만큼만 줄었다.
- **비율이 사례마다 다른 이유:** T2·T3 평가가 큰 사례(상수도관·CDW·전산장비)에서는 같은 0.5초가 작은 비율(2.7~6.5%)이고, 평가가 짧은 사례(EV·멀티모달)에서는 10% 안팎이 된다.
- **M35 예상과 맞다.** 실제 1건 실행에서 예상한 "최대 약 1초, 전체의 약 7%"와 같은 범위다.

## 5. 결론

| 판정 기준 | 결과 | 충족 |
|---|---|:---:|
| 결과 동일 | 모든 쌍 동일(점수 미세 차 제외) | ✅ |
| T1.5 이후 구간 20% 이상 단축 | 중앙값 2.7% | ❌ |

- **기본값은 순차로 유지한다.** 병렬은 `workflow_mode="parallel"`(`run_langgraph_review.py --workflow-mode parallel`) 선택 기능으로 둔다.
- 속도를 올리려면 병렬화보다 다음 두 곳이 먼저다.
  1. **T2·T3 평가 캐시:** T1.5 이후 구간의 27~83%. T3 후보의 과거 RFP를 매번 다시 읽어 개요를 재계산한다(`agent23_evaluation._source_profile`). 색인 때 만든 개요와 파일 SHA-256을 저장해 두고 해시만 대조하면 된다.
  2. **T1 추출:** 4~20초. 페이지 수에 비례한다(쪽마다 pypdf·pdfplumber 두 번 읽기 + 표 추출).

## 6. 실측 중 발견한 것

1. **공고 식별 오탐 (수정 필요):** 통합정보시스템 공고문의 기관 자체 공고번호 "2026-013"(`[제2026-013호]`)을 나라장터 공고번호 R26BK01747679와 비교해 "공고 식별 충돌"로 판정한다. 이 충돌은 담당자가 승인해도 넘어가지 않게 막혀 있어, 시연 사례인 이 공고는 T2로 갈 수 없다. 기관 공고번호 형식은 나라장터 번호와 비교하지 않아야 한다.
2. **임베딩 비결정성:** 같은 입력에서도 점수가 소수 넷째 자리에서 흔들려, 임계값 경계 후보가 실행마다 들어갔다 빠진다. 재현성이 필요하면 질의 임베딩을 텍스트 해시 기준으로 캐시한다.
3. **비교 기준 보완:** 처음에는 모든 쌍이 "결과 다름"으로 나왔다. 실행 시각(`checked_at`)과 위 점수 흔들림 때문이었다. 비교 스크립트가 실행 시각을 빼고 점수 차 0.002까지 같은 결과로 보도록 고쳤다(`result_difference`). 판정·후보·순서 같은 나머지 값은 정확히 같아야 같은 결과로 본다.
