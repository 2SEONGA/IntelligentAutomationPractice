# M39 일원화 보완(live·공고번호), 공고 식별 오탐 수정, T2·T3 평가 캐시

- 작업일: 2026-11-20
- 순서(이성아 요청): M38의 남은 한계 → 공고 식별 오탐 → T2·T3 평가 캐시

## 1. 남은 한계 ①: 직접 업로드 건의 공고번호

**문제:** 공고함에서 시작한 건만 공고번호가 저장돼, PDF를 직접 올린 건은 나라장터 조회·교차검증·체크리스트 K2·K3 자동 판정을 모두 건너뛰었다. 시연 문서에서는 RFP에서 공고번호가 읽히지 않고(3건 모두), 공고문도 상수도관은 못 읽고 통합정보는 기관 번호만 읽혀서, 문서에서 읽은 번호로 자동 조회하는 방법은 효과가 없었다.

**수정:**
- 업로드 화면에 "나라장터 공고번호 (선택)" 입력칸. 형식이 틀리면(기관 자체 번호 포함) 화면에서 안내하고 시작 버튼을 막는다.
- `POST /api/runs`가 `notice_no`를 받아 나라장터 형식(`R26BK01762350`, 구 형식 `20240112345`, 차수 `-000` 선택)만 허용하고 `upload.json`에 저장. 아니면 400.
- 작업 실행기(`langgraph_job.notice_key`)가 `notice_attachment.json`(공고함) 다음으로 `upload.json`을 읽는다.
- 형식 판별은 `state_history.parse_g2b_notice()` 한곳에 둔다(오탐 수정과 공용).

## 2. 남은 한계 ②: live 모드를 LangGraph로

**문제:** M38 뒤에도 live 웹 실행은 CrewAI 경로(`run.py`)였다. 검증 없이 보고서를 먼저 만드는 구조가 live에 남아 있었다.

**수정 (절충안 2단계):**
- `BidReviewCrew.brief()`로 live 단계(compact 요약 → CrewAI Agent 4개 → 의사결정 요약 검증 → `debug/agent_0*_summary.json`)를 떼어 냈다. 기존 `run --mode live`도 이 함수를 쓴다.
- 웹 live 실행: LangGraph(T1 → T1.5 → 승인 → T2 → T3 → T4)가 끝난 뒤 **T4가 검증한 결과만** `brief()`에 넘겨 브리핑을 받고 보고서의 `agent_executive_summary`·"CrewAI 의사결정 요약" 절로 붙인다. 판정 상태는 규칙 기반 T4 결과 그대로다. `crew_execution_manifest.json`에 파이프라인을 기록한다.
- T1.5에서 멈춘 건은 브리핑하지 않고, 승인해서 T4까지 간 뒤에 브리핑한다(승인 요청이 그만큼 길어짐, 실측 50초).
- 오류 진단 파일(`crew_live_error.txt`)은 OpenAI·나라장터 키 값을 가린다(`_redacted`).
- **아직 run.py로 남은 것:** live에서 "나라장터 시장조사"(낙찰 실시간 조회)를 켠 실행. CrewAI 시장 Agent가 실시간 낙찰 조회를 쓰기 때문이다. T3 낙찰 연결과 합칠지는 별도 결정.

**실측 (상수도관, 실제 작업 프로세스·실제 OpenAI 호출):** 업로드(공고번호 입력) 15.9초 → T1.5 중단(나라장터 `found`) → 승인 50.4초 → T4 + CrewAI 브리핑("보류 — 사업금액 내부 기준 미달, 필수 증빙 미확인"). 보고서 판정 보류(규칙 기반).

## 3. 공고 식별 오탐 수정

**문제 (M37 발견):** 공고문의 기관 자체 번호 "2026-013"(`[제2026-013호]`)을 나라장터 번호 R26BK01747679와 비교해 "공고 식별 충돌"로 판정했다. 이 충돌은 승인으로도 못 넘어가고, 나라장터 조회까지 건너뛰어 통합정보시스템은 T2로 갈 수 없었다.

**수정 (`state_history.case_identity`):** 문서에서 읽은 번호는 나라장터 형식일 때만 비교·조회에 쓴다. 기관 번호는 `agency_notice_numbers`에 참고로만 남긴다. 입력 공고번호가 없으면 문서에서 읽은 나라장터 번호를 조회에 쓴다. 나라장터 형식끼리 다르면 지금처럼 충돌이다.

**확인:** 통합정보시스템 → 식별 `identified`(충돌 없음), 기관 번호 `["2026-013"]`, 나라장터 조회 `found`, 승인 후 T4까지 도달(28.4초). 테스트의 가짜 공고번호(`N100`)는 나라장터 형식(`R26BK00000100`)으로 바꾸고, 기관 번호 비교 안 함·문서 번호로 조회·나라장터 번호끼리 충돌 테스트를 추가했다.

## 4. T2·T3 평가 캐시

**문제 (M37):** `t23_evaluate`가 T3 후보 RFP 원문에서 개요를 매번 다시 만들어 상태의 발췌와 대조했다. T1.5 이후 구간의 27~83%.

**수정 (`agent23_evaluation._source_profile`):** 개요를 `outputs/rag/profile_cache.json`에 저장하고, 키를 **원문 파일 SHA-256 + 사업명 + 기관 + 개요 추출 코드(`past_projects.py`·`project_profile.py`) 해시**로 잡았다.
- 원문이 한 바이트라도 바뀌거나 추출 코드가 바뀌면 다시 계산한다.
- 발췌 대조는 그대로 "실제 원문에서 만든 개요" 기준이라, 상태의 발췌가 변조되면 여전히 보류로 걸린다.
- 저장 실패는 평가를 막지 않고, 임시 파일 후 교체로 반쯤 쓴 캐시를 남기지 않는다.

**실측 (상수도관):**

| | 수정 전 | 수정 후(캐시 있음) |
|---|---:|---:|
| `t23_evaluate` | 7.47초 | **0.01초** |
| 전체(T1→T4, 승인 포함) | 14.4초 | **7.3~8.3초** |
| 원문 대조 결과 | 5건 통과 | 5건 통과(동일) |

캐시가 없는 첫 실행은 이전과 같은 시간(8.8초)이 걸리고, 같은 후보가 다시 나오면 빨라진다. 이제 가장 큰 구간은 T1 추출(4~20초)이다.
