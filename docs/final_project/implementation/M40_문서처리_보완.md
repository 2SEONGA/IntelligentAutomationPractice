## 1. 겹친 글자 거르기

**문제:** 과거 RFP 2건(R26BK01550694, R26BK01693931)은 굵은 글씨를 같은 글자로 조금씩 비켜 겹쳐 찍었다. pdfplumber는 "제제 안안 요요 청청 서서", pypdf는 "사 업 명사 업 명"처럼 글자를 겹쳐 읽었다. T1은 두 추출기 중 더 긴 텍스트를 쓰므로 겹친 쪽이 그대로 채택됐고, T3 사업 개요에도 같은 텍스트가 들어갔다.

**수정:**
- 새 공용 모듈 `src/bid_review/pdf_chars.py`의 `dedupe_overprint()`는 pdfplumber `dedupe_chars(tolerance=1)`로 1pt 안에서 같은 글자·글꼴·크기가 겹치면 하나만 남긴다. 실패하면 원래 쪽을 그대로 쓴다.
- T1(`agent01_rfp.RFPExtractor._page_text`): 겹침이 있는 쪽은 pypdf 대신 걸러낸 pdfplumber 텍스트를 쓰고, 표 추출도 걸러낸 쪽에서 한다. 쪽 분석 기록에 `pdfplumber_dedupe_chars`를 남긴다.
- T3(`past_projects._rfp_pages`): 쪽 텍스트를 걸러낸 쪽에서 읽는다.
- `scripts/compare_ocr_extraction.py`도 T1과 같은 추출(`_page_text`)을 쓰도록 맞췄다.

**확인:** R26BK01550694 1쪽 "제제 안안 요요 …" → "제 안 요 청 서 / 사 업 명 AI 플랫폼(KEXIM AI) 구축 / 주관기관 한국수출입은행". 시연 RFP 중에서는 통합정보시스템 표지 1쪽만 겹침이 있었다(478자 중 420자가 그림자 글자).

## 2. 서식 표식(별첨·별표·양식)

**문제:** "별첨·별표·양식" 서식 쪽이 본문으로 분류됐다. 그렇다고 글자가 있는지만 보면 본문 인용까지 서식 쪽이 된다. 처음 시도에서 "[별첨]의 평가기준", "별첨으로 제출", "[별표1] 참고" 같은 본문 쪽이 서식 쪽이 되면서 CDW 계약기간 선택 값이 4쪽 값에서 12쪽 값으로 바뀌었다.

**수정 (`_classify_page`):**
- 기존 표식(별지·서식·붙임·첨부)은 그대로 둔다.
- 별첨·별표·양식은 **쪽 앞 3줄 안에 표제 형태**(`<별표 2>`, `[별첨 1]`, `【양식 3】`, `별표 4.`)로 나올 때만 서식 쪽으로 본다.
- 표 중심 쪽은 표 행 단위로 요구사항을 읽으므로, 머리 표제가 있어도 표 쪽으로 둔다. 서식 쪽으로 바꾸면 CDW 참가자격 1건의 문장이 표 행에서 본문 줄로 바뀌고, 요구사항이 96건에서 117건으로 늘었다.

## 3. 같이 고친 부작용

- **표지 OCR 오탐:** 겹친 글자를 거르자 통합정보 표지가 38자("통합정보시스템 고도화 구축 / 제안요청서 / 2026. 09")가 되어 40자 기준으로 "OCR 필요"가 됐다. 표지는 원래 짧으므로, **글자가 하나도 없을 때(스캔본)만** OCR 대상으로 본다. 본문 쪽 기준(40자)은 그대로다.
- **사업명 후보:** 표지에서 띄어 쓴 "제 안 요 청 서"가 사업명 후보로 들어갔다. 표지 후보 제외 조건을 띄어쓰기와 무관하게(`제\s*안\s*요\s*청\s*서`, `목\s*차`) 바꿨다.

## 4. 공고문 HWP·HWPX (QA #3)

**문제:** 공고문은 PDF만 받았다. 이름이 `.pdf`인 공고문만 공고문으로 분류하고, 다운로드와 바이트 대조가 파일 앞부분 `%PDF-`만 허용했다. 저장 이름 `notice.pdf`도 여러 곳에 고정돼 있었다.

**수정:**
- `notices.py`
  - `NOTICE_MAGIC`(PDF `%PDF-`, HWPX `PK\x03\x04`, HWP OLE 서명)과 `notice_suffix()` 추가. 이름에 공고 표현이 있는 `.hwp`·`.hwpx`도 공고문으로 분류한다.
  - `fetch_attachments`: PDF → HWPX → HWP 순으로 받고 형식별 magic을 확인한 뒤 `notice.pdf`/`notice.hwpx`/`notice.hwp`로 저장한다. 실제로 받은 첨부를 `notice_attachment`로 돌려준다(PDF가 실패해 HWP를 받은 경우 기록이 맞도록).
  - `compare_notice_pdf_bytes`: 저장한 파일과 **같은 형식의 첨부**를 골라 대조하고, 형식 magic이 다르면 대조하지 않는다. 상태 이름(`download_not_pdf` 등)은 기존 화면·기록과 맞추려고 그대로 둔다.
- `runs.py`: `NOTICE_FILES`, `notice_file(folder)`로 검토 폴더의 공고문을 찾는다(PDF 우선).
- `app.py`·`jobs.py`: 공고함 시작, 업로드 재사용, 핵심정보 재검토, 실행 명령(`--notice-pdf`)이 저장된 공고문 파일을 찾는다. 파일이 아직 없으면 예전처럼 `notice.pdf` 경로를 넘긴다.
- T1(`_extract_hwp_pages`): `.hwp`·`.hwpx`는 `hwp_text`로 읽고 50줄을 한 쪽으로 본다(T3와 같은 값, `hwp_text.hwp_pages`로 공용화). 표·OCR 판정은 하지 않는다.

**남은 것:** 웹 직접 업로드는 여전히 공고문 PDF만 받는다. 실제 HWP 공고문 1건의 나라장터 바이트 대조는 API 키·네트워크가 필요해 가짜 응답 테스트로만 확인했다.

- 해제 89쪽: 대부분 "반복 문자 또는 기호 비율이 높음"이었다. 겹친 글자 2건이 43쪽, 나머지는 겹침이 일부 있던 다른 과거 RFP에서 나왔다.
