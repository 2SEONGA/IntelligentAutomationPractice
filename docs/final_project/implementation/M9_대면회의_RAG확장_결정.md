# M9 대면 회의 내용 검토 및 RAG 확장 결정

작성일: 2026-11-16  
상태: 회의 제안 검토·방향 합의·Agent 2 데이터 감사 및 검색 스키마 초안 완료. 인덱싱/검색 구현은 미착수.

## 요약

- **한 일:** 11-16 대면 회의 제안을 검토해 Agent 2(자사 실적)·Agent 3(과거 RFP) RAG 방향을 정하고, ㈜아이티센엔텍 공개자료 11건을 감사해 별도 FTS5 인덱스를 만들었다.
- **결과:** 법인 경계 보존, RAG 유사도로 자격·참여를 자동 확정하지 않음, 10억 기준은 채택하지 않음.
- **남은 일:** 회사 자료 의미 검색(M21)·Agent 3 과거 사업 검색(M23) 구현. 과거 RFP 수집 범위 확대.

## 목적

2026년 11월 16일 대면 회의 PDF에서 나온 구현 제안을 현재 코드·데이터와 대조하고, 추가 구현 우선순위와 경계를 정리한다.

## 회의 자료에서 확인한 제안

- **Agent 2 RAG**: Agent 1이 추출한 요구사항을 질의로 삼아 자사 기술·수행 사례·인력 관련 근거를 검색한다. 검색된 유사 사례는 자격 충족으로 자동 확정하지 않고 금액·기간·실제 수행 여부 등 증빙을 확인한다.
- **Agent 3 RAG**: 과거 공공사업 RFP/공고의 사업 목적·수행 범위·핵심 기술을 검색해 신규 사업과 비교한다. 과거 RFP 검색은 나라장터 실시간 조회와 분리할 수 있다. 낙찰 정보는 연결할 근거가 있을 때 함께 제시한다.
- **회사 실적 범위**: 그룹사 자료가 섞여 대상 회사의 실적으로 오인되지 않도록 특정 법인 실적만 사용한다.
- **금액 구간**: 10억 기준을 추가할지 제안되었지만, 내부 정책 합의 전에는 현행 기준을 바꾸지 않는다.
- **안전장치·평가**: RAG 근거·출처를 보여주고, 자동 판단이 불확실하거나 충돌할 때 재검색 또는 담당자 검토로 보낸다. 수치·명시 규칙은 Python 검증으로, 의미 비교는 평가 단계와 사람 검토로 다룬다.

## 현재 구현과 자료 확인

- 현재 T1.5는 금액·참가자격·기간에 대한 원문 근거 검색/검증을 수행한다. 검색은 SQLite FTS 키워드 검색이며 임베딩 기반 벡터 검색은 아니다.
- LangGraph에는 T1 → T1.5 검증 → 조건부 추가 검색/담당자 검토 → 승인 시 T2로 이어지는 흐름이 있다.
- `data/company/company`는 JSON 자료로, 확인 당시 `company_name`은 ㈜아이티센엔텍, `records` 11건, `sources` 7건, `missing_evidence` 5건을 포함한다. 자료의 자체 사용 규칙은 공개 근거 기반 사전 검토용이며, 개별 입찰의 실적 인정·인증 유효성·인력 투입 가능성을 이 데이터만으로 확정하지 않도록 하고 있다.
- 과거 나라장터 낙찰 데이터는 `data/market/itcen_group_awards_3y.json`으로 사용되고, 시장 모듈은 키워드 교집합으로 유사성을 선별한다. 이 흐름은 과거 RFP 원문을 의미 검색하는 RAG와 다르다.
- 회의 자료에는 과거 RFP의 실제 확보 건수와 낙찰 데이터 연결키가 확정되어 있지 않다.

2026-11-16 기준 재무 출처 최신성을 점검했다. 회사 재무 페이지는 2025년 기말 연결재무를 표시한다. [회사별 공시 목록](https://www.k5.co.kr/stock/010280/official_notice)에는 2026년 9월 기준 3분기 보고서가 2026-11-12 등록된 것으로 나와 DART 원문 링크까지 확인했지만, DART 원문 열람은 502 오류로 실패했다. 따라서 보고서 내용과 회계 범위를 확인할 때까지 기존 2025년 수치를 최신 자료처럼 사용하지 않는다. 기존 KIND 사업보고서 및 2026년 1분기 보고서 원문은 열어 확인했다. 회사 웹페이지 세 곳은 검색 색인에서 관련 본문을 확인했으나 직접 페이지 열람은 시간 초과되어 본문 전체·첨부·갱신일을 재검증하지 못했다.

## 확인한 데이터 보완

`data/company/company`의 CAP-PROJECT-001~004에 SRC-003의 **2026-03-31 기준 보고 진행률**과 출처 ID를 추가했다. 값은 HUG 60.81%, 통합징수 37.31%, KCTC 24.59%, 복권시스템 100.00%다. 이는 분기보고서에 기록된 진행률이며, 검수 완료나 실적증명서 발급을 뜻하지 않는다고 각 기록에 명시했다. 특히 100%도 발주처 인수/검수 문서와 동일한 뜻으로 취급하지 않는다.

재무 record에는 2025-12-31 연결 기준이라는 범위·기준일과 `latest_filing_pending_primary_source_review` 상태를 추가했다. SRC-008은 2026년 3분기 보고서의 확인 후보 원문 링크로 등록했으나, 본문을 확인하지 못해 어떤 3분기 금액도 옮기지 않았다.

## Agent 2 로컬 검색 인덱스 1차 구현

- `src/bid_review/rag/company_retriever.py`는 회사 JSON record를 검색 가능한 문장으로 구성하고, record/source/법인 경계/검증 요구사항을 검색 결과 metadata로 보존한다.
- `scripts/build_company_rag_index.py`는 `outputs/rag/company_retrieval.sqlite3`에 별도 SQLite FTS5 인덱스를 만든다. 기존 RFP 페이지 인덱스와 분리되어 있다.
- `scripts/search_company_rag.py`는 검색 결과를 JSONL 형태로 출력하고 출처 URL·섹션·증거 수준·미확인 사항을 함께 제공한다.
- 인덱스 생성 결과는 11 records, 대상 법인은 ㈜아이티센엔텍이며 다섯 정규화 record type이 들어간 것을 확인했다.
- 이는 키워드 검색 baseline이다. 임베딩/벡터 검색은 아니며, 실제 LangGraph T2/UI 연결은 M10에서 진행한다. RAG 검색 순위는 적합성 판정으로 사용할 수 없다.

재생성/검색 명령:

```bash
PYTHONPATH=src python scripts/build_company_rag_index.py
PYTHONPATH=src python scripts/search_company_rag.py "요구사항 검색어" --record-type project_reference
```

## 합의된 결정

1. RAG 확장 순서는 **Agent 2 → Agent 3**로 한다.
2. Agent 2의 초기 데이터 후보는 `data/company/company`이며, 자료 내 대상 회사 기준을 따른다.
3. 프로젝트 대상 법인은 **㈜아이티센엔텍으로 고정**한다. 그룹사나 다른 법인의 낙찰/수행 이력을 이 법인의 실적으로 간주하지 않는다. 공동수급 등 실제 실적 귀속을 단정하기 어려운 건은 별도 확인 상태로 둔다.
4. 내부 정책을 확인하기 전까지 사업금액 관련 **현행 40억·100억 기준을 유지**한다. 10억 구간은 추가하지 않는다.
5. 유사도 검색은 후보를 찾는 보조수단이다. 근거 원문 및 법인/실적 증빙을 확인하기 전 자동으로 자격 충족·Go 판단을 내리지 않는다.

### 자료 모델의 검색 전 정규화 규칙

- 모든 검색 결과에 `company_legal_entity=㈜아이티센엔텍` 필터/경계값을 넣는다. `former_name`은 문서 검색 별칭일 뿐 별도 법인이나 그룹사 결과를 합치는 근거가 아니다.
- `record_type`은 `identity`, `business_capability`, `certification`, `project_reference`, `financial_reference`로 정규화한다.
- 실적 근거에는 `project_status`(진행 중/종료기재/미확인), `project_role`(단독/컨소시엄/미확인), `amount_basis`(계약 총액/회사 귀속액/추정 사업 규모/미확인), 계약 기간과 검증 요구사항을 필드로 둔다.
- 재무에는 `period_end`, `accounting_scope`(별도/연결), 지표/통화, 출처를 명시한다. 별도와 연결 수치를 섞어 비교하지 않는다.
- 검색 chunk는 근거 문구 단위로 만들되 `record_id`, `source_id`, source URL, 섹션, 수집/확인 일자, 문서 판본, 법인 범위, 증거 수준, 원래 record 전체를 추적할 수 있게 한다.
- `CAP-LEGAL-001`은 모든 요구사항과 일반 의미 유사성 검색에 섞지 않고 법인 확인용 조회에서만 사용한다. 재무/인증/진행 중 계약도 서로 다른 요구 유형에서만 검색한다.

## Agent 2 검색 입출력 스키마 초안

### 입력 `CapabilitySearchRequest`

| 필드 | 설명 |
|---|---|
| `notice_id` | 현재 입찰/검토 실행 ID |
| `requirement_id` | Agent 1 요구사항 ID |
| `requirement_text` | 원문 근거를 보존한 요구사항 문구 |
| `requirement_category` | 기술, 유사실적, 인증, 재무, 인력, 법인자격 등 |
| `required_evidence` | 원문이 요구하는 증빙 유형·기간·금액·발주처 조건 |
| `query_text` | 검색에 사용할 요구사항 및 정규화된 기술/업무 개념 |
| `target_legal_entity` | 고정값 ㈜아이티센엔텍 |
| `limit` | 반환 상한(초기 기본값 제안 5) |

### 결과 `CapabilityEvidenceCandidate`

각 결과는 `record_id`, `source_id`, `title`, `record_type`, `excerpt`, `source_url`, `source_section`, `source_checked_at`, `evidence_level`, `entity_scope`, `project_status`, `project_role`, `amount_basis`, `period`, `relevance_score`, `relevance_reason`, `requirement_gaps`, `verification_required`, `review_status`를 포함한다. 유형에 해당하지 않는 필드는 null로 두고, 연결/별도·진행/완료·총액/귀속액 구분을 하나의 요약 문장에 뭉개지 않는다.

`review_status`는 초기에는 `candidate`, `needs_document_check`, `conflict`, `not_relevant`를 사용한다. `matched/eligible` 같은 자격 충족 상태는 Agent 2 검색 결과에서 자동 생성하지 않는다. 입찰 참가 자격 충족 여부는 공고 요구사항과 원본 증빙을 확인하는 별도 판단이다.

## 제안하는 구현 순서

### M9-A: Agent 2 자료 확인·검색 설계·로컬 인덱스 — 1차 완료

- 11개 record의 출처 유형과 주요 증빙 한계를 1차 분류했다. 원본 페이지 전수 확인과 최신성 갱신은 남아 있다.
- Agent 1의 요구사항 범주를 입력·출력 스키마에 연결했다.
- 법인 범위, 진행/완료 상태, 컨소시엄 총액/회사 귀속액, 별도/연결 재무를 구분하는 필드를 정의했다.
- 대상 법인 조건을 강제하는 별도 SQLite FTS5 회사 자료 인덱스를 만들고 11건을 적재했다.
- CLI 검색기는 출처와 미확인 요구사항을 반환한다.
- 현재 FTS 검색을 기준선으로 둘지, 임베딩/Vector Store를 먼저 도입할지 M4에서 선택한다.
- 테스트 질의와 담당자 정답 판단을 준비해 검색 누락과 잘못된 법인 귀속을 확인한다.

### M9-B: Agent 2 LangGraph·UI 연결 — 코드 반영 완료, 실행/화면 확인 미실행

- T1.5 통과 또는 담당자 승인 후 회사 증거 검색 노드를 실행하고, 결과 후보를 T2 `RequirementMatch`에 연결한다.
- 후보는 기존 결정론적 점수/상태를 바꾸지 않고 별도 필드로 보존한다. 직원 근거 확인은 출처·검증 한계를 보며 수행한다.
- 이 작업에서 회사 출처 원문 링크와 검증 요구사항을 검토 탭에 표시하도록 연결했다. 화면 빌드/브라우저 확인과 실제 T2 시연은 아직 안 했다.
- 현재 연결은 LangGraph 경로의 결정론적 `CapabilityMatcher`까지다. 별도 CrewAI live Agent 2가 이 후보 목록을 입력받는 연결은 범위 밖으로 남아 있다.

### M9-C: Agent 3 과거 사업 RAG

- 확보 가능한 과거 공공사업 RFP/공고 자료 범위를 정하고, PDF 페이지·문서 판본·사업 ID 메타데이터를 보존한다.
- 신규 사업 개요/수행 범위로 Top-K 사업을 검색하고, LLM 또는 규칙 기반 비교에서 공통점·차이점을 근거와 함께 제시한다.
- 낙찰기업/금액은 확실한 사업 ID 연결이 있을 때만 노출하고, 없으면 미확인으로 남긴다.
- 사전 수집 corpus 검색과 실시간 나라장터 API 조회를 별도 출처로 표시한다.

### M9-D: 공통 평가 및 종료 기준

- 검색 적합성, 근거 인용 존재/정확성, 법인 귀속, 판단 근거의 타당성을 별도로 평가한다.
- 금액 등 명확한 값은 규칙 기반 비교를 우선하고, 의미 유사도는 최종 판정 자체로 사용하지 않는다.
- 반복 검색으로 해결되지 않거나 상충 근거가 남으면 Human Review로 종료한다.

## 미해결 사항

- 11개 회사 자료 record의 출처 성격과 핵심 한계를 대조했으나, 원본 페이지/공시의 모든 문장·값을 전수 검증한 것은 아니다.
- 회사 사이트 페이지는 검색 결과로 요지를 확인했지만 직접 접속이 실패해 전체 페이지와 첨부 자료·갱신일 확인이 남았다.
- 2026년 3분기 보고서 등록 및 DART 원문 링크는 공시 목록에서 확인했으나 원문 열람은 실패했다. 재무 수치를 옮기기 전에 공식 원문을 다시 열어 별도/연결 기준과 대상 회사를 검증해야 한다.
- Agent 2에서 공개 자료와 실적 증빙(계약/실적증명)을 어떤 상태로 구분해 표시할지 세부 스키마가 필요하다.
- Agent 3 과거 RFP 확보 범위, 수집 방법, 문서 ID와 낙찰 데이터의 매핑 가능성을 조사해야 한다.
- 임베딩 공급자/로컬 모델 및 Vector Store 선택은 미정이다. 현 FTS 검색과 의미 검색을 비교하는 작은 기준선 평가 후 결정할 수 있다.
- 담당자 정답 라벨과 평가 질의가 아직 없다.
- 내부 정책이 확인되기 전까지 10억 기준 변경은 보류한다.
