# M28 Agent 3 과거 RFP 수집 전체 조회 전환

작성일: 2026-11-17  
상태: 코드·테스트 완료, 180일 후보 수 라이브 확인. **실제 수집(첨부 다운로드)은 미실행** — M24와 같이 첨부파일정보 API 일일 할당량이 초기화된 뒤 실행.

## 요약

- **한 일:** Agent 3 과거 RFP 수집도 M27과 같이 키워드 없는 전체 조회로 바꿨다. M27에서 `collect_keywords`를 비우자 Agent 3는 보조 키워드 10개(상수도·GIS·임상 등)만으로 수집하게 되어 오히려 범위가 좁아진 상태였다. 함께 낙찰 조회(`fetch_awards`)가 첫 페이지 999건만 읽던 문제를 고쳤다. 키워드 없이 조회하면 한 주 낙찰이 999건을 넘어 나머지가 조용히 빠졌을 것이다.
- **결과:** 180일(2026-05-20~11-16) ICT 서비스 후보가 키워드 방식 2,493건(M23) → **10,530건**으로 늘었다(1억 이상 7,116건). 기존 저장 80건은 모두 이 후보 안에 있어 이어받기가 그대로 동작한다. 백엔드 테스트 16개 파일 통과.
- **남은 일:** 할당량 초기화 후 `scripts/build_past_projects.py` 실행(M24 남은 일과 같음). 후보가 4배 늘어 하루 800회 조회로는 일부만 확인하므로, **어떤 공고부터 받을지(현재: 주 단위로 최신부터 고르게)** 정할 필요가 있다. 후보 목록 조회에 약 8분이 걸리고 실행할 때마다 반복된다.

## 변경 내용

| 파일 | 변경 |
|---|---|
| `src/bid_review/rag/past_projects.py` `collect_past_projects()` | `collect_keywords`가 비면 `[""]`(전체 조회). 키워드가 있을 때만 `extra_keywords`를 보탬. 로그에 "전체 수집" 표시 |
| 같은 파일 `fetch_awards()` | `totalCount`까지 페이지를 따라감. 오류 응답은 이전처럼 실패 구간으로 셈 |
| `config/settings.yaml` `past_projects.extra_keywords` | 키워드 수집일 때만 쓴다는 주석 |
| `tests/test_semantic.py` | 낙찰 조회 2페이지 읽기, 현재 설정에서 수집이 키워드 없이(`""`) 조회하는지 확인 |

- ICT 서비스 후보 **10,530건**, 이미 저장된 과거 RFP 80건 모두 포함, 1억 이상 7,116건
- 소요 7분 52초

## 결정이 필요한 것

후보 10,530건 중 하루 최대 800건만 첨부를 확인한다(저장 목표 200건). 현재 순서는 "주마다 최신 공고부터 한 건씩"이라 기간은 고르게 덮지만 사업 규모·성격은 고르지 않는다.

| 선택지 | 영향 |
|---|---|
| 현재대로 (주 단위 최신순) | 소규모 홈페이지·장비 유지보수도 많이 섞임. 세 시연 공고(1.07억·3억·10.7억)와 비슷한 규모가 자연스럽게 포함 |
| 주 안에서 금액 큰 순 | 회사 주력(40억 이상 SI·유지관리)과 비슷한 사업 위주. 소규모 시연 공고와는 덜 비슷할 수 있음 |
| 금액 하한(예: 1억 이상만) | 후보 7,116건. 잡음은 줄지만 기준값은 근거 없이 정하게 됨 |

- 낙찰 페이지 처리는 가짜 API 테스트로만 확인했다. 키워드 없는 낙찰 조회가 7일 구간에서 실제로 허용되는지는 수집 실행 때 `award_failed_windows`로 확인해야 한다.
