# M12 복수 출처 교차검증 설계

작성일: 2026-11-16  
상태: 설계 초안 완료. 라이브 API 재조회와 첨부 공고문 연동은 후속 구현.

## 요약

- **한 일:** RFP PDF·나라장터 API·공고 상세 링크·첨부 원문의 역할과 필드별 교차검증 규칙을 설계하고, citation 링크를 공고별 상세 URL 우선으로 바꿨다.
- **결과:** `bidClseDt`를 제안서 기한으로 간주하지 않는 원칙 확정.
- **남은 일:** 참가자격 API·첨부 교차검증, 공고문 색인 구현.

## 배경과 결정

담당자 검토에서 `g2b_crosscheck_budget_krw`의 링크가 공고별 데이터 레코드를 직접 가리키지 않아 확인 완료로 판정할 수 없었다. PDF만 검색하는 구조로는 나라장터의 구조화 정보, 공고별 상세 페이지, 공고 첨부문서를 함께 확인하기 어렵다.

T1.5는 주장별로 적합한 출처를 구분해 연결하고 PDF·API·공고 상세 링크·첨부 원문을 교차 확인한다. 출처가 없거나 열리지 않으면 통과로 추정하지 않고 담당자 확인으로 보낸다.

## 출처별 역할

| 출처 | 확인 대상 | 처리 원칙 |
|---|---|---|
| RFP 원본 PDF | 사업금액의 명칭·VAT·범위, 참가자격 조항, 계약기간, 제출기한 문구 | 페이지와 원문 인용 보존 |
| 나라장터 구조화 API | 공고번호·차수, 배정예산(`asignBdgtAmt`), 추정가격(`presmptPrce`), 입찰 마감(`bidClseDt`), 첨부목록 | 공고번호·차수로 조회. 필드명, 값, 응답 시각, 실제 공고 URL, API 명세 URL 보존 |
| 공고별 상세 링크 | 해당 공고와 정정 정보의 사용자 확인 | 공고번호와 차수를 담은 링크 사용. 링크 접근 가능성과 데이터 검증 상태를 따로 기록 |
| API에서 찾은 공고 첨부 PDF | 제안서 제출기한, 제출 방식, 정정·예외 문구 | RFP와 별도 문서로 저장·색인. 첨부 식별자, URL, 해시, 페이지·인용 보존 |

현재 사용하는 공공데이터포털 공식 명세는 2026-11-10 수정되었고 최신 Base URL은 `BidPublicInfoService02`로 안내한다. 공고번호·차수 기반 조회와 첨부파일 정보 조회가 제공된다. API 변경에 맞춰 구현 시점에 요청/응답 필드와 조회 기간 제한을 재확인한다. [공식 입찰공고정보서비스 명세](https://www.data.go.kr/data/15129394/openapi.do)

## 필드별 교차검증

### 금액

- RFP의 사업금액/사업예산/추정가격과 API의 배정예산/추정가격은 이름이 비슷해도 별도 필드로 유지한다.
- 업무상 의미, VAT 기준, 총액/연차 범위가 같은 근거가 있을 때 비교한다.
- 10% 차이만으로 VAT 포함/별도를 자동 판정하지 않는다.
- API 명세 페이지가 아니라 해당 공고 레코드와 필드 인용이 근거에 포함되어야 한다.

### 참가자격

- RFP와 공고 API/첨부에서 업종·지역 제한·공동도급·참가 제한을 확인한다.
- API 제한 코드와 변환한 설명을 함께 보존한다.
- 출처 간 충돌은 자동 선택하지 않고 `conflict`로 담당자에게 보낸다.

### 기간·기한

- 계약기간은 RFP/과업지시서로 확인한다.
- 입찰서 마감은 API의 `bidClseDt`와 정정 이력으로 확인한다.
- `bidClseDt`를 제안서 제출기한으로 자동 간주하지 않는다. 제안서 기한은 API가 직접 제공하지 않으면 API 첨부목록에서 입찰공고문 PDF를 찾아 그 원문에서 확인한다.
- 제안서 제출, 입찰서 제출, 질의기한, 공동수급협정 마감은 서로 다른 일정으로 구분한다.

## 근거 메타데이터와 LangGraph State

각 근거에 `source_type`(RFP PDF/API/공고 상세/첨부), `source_id`, 공고번호·차수, 필드명·값, 페이지·인용, 실제 출처 URL, API 명세 URL, 조회시각, 문서 해시/버전, 접근 상태를 둔다.

LangGraph State는 `notice_identity`, `api_record`, `attachments`, `source_fetch_status`, `source_evidence`, `verification`을 분리한다. API 키 누락, 통신 오류, 링크 차단, 첨부 누락은 각각 원인을 기록하고 Human Review로 라우팅한다. 키는 State·로그·화면에 넣지 않는다.

## Workflow 및 라우팅

`T1 추출 → 공고번호·차수 확정 → G2B API 단건 조회 → 필요한 공고 첨부 수집 → 출처별 검색·비교 → 충분한가?`

- 적합한 출처에서 의미와 값이 확인되면 `confirmed`
- 추가 API/첨부 검색이 가능하면 `retrieve_more`
- 출처 불일치·접근 실패·필드 의미 불명확이면 `human_review`
- T2는 자동 검증 통과 또는 사유를 남긴 담당자의 명시 승인 뒤 실행

정정 차수는 현재 공고 식별자와 연결하고 최신 값을 우선하되, 이전 값과 변경 이력을 감사 자료로 남긴다.

## 구현 순서

1. 최신 명세 기준으로 공고번호/차수 단건 API 및 첨부 조회 어댑터 구현
2. 공고별 링크를 우선 출처로 표시하고 API 명세 링크는 별도 표시
3. 공고문 첨부를 RFP와 다른 문서종류·해시·페이지로 RAG 색인
4. 금액·참가자격·기간 필드별 source mapping과 conditional routing 구현
5. 자동 후보가 T1 값·T2 점수에 승인 없이 합산되지 않는지 확인

## 이번 공고에 적용할 판정

- 담당자는 금액의 나머지 항목, 참가자격 전체, 계약기간을 확인 완료했다.
- `g2b_crosscheck_budget_krw`는 공고별 출처 정확성 문제로 미확인 상태를 유지한다.
- `proposal_deadline`은 RFP의 “입찰공고문 참조”만으로 완료 처리하지 않는다. 공고 API 및 연결된 첨부 공고문에서 확인한다.
- T2 승인은 별도이며 아직 승인되지 않았다.
