# 지능형자동화실습 기말 팀프로젝트 — 팀원별 보완사항

## 1. 인진은 — T1.5 근거 선택 및 T3 과거 사업 데이터

### 보완 1. T1.5 추가 검색 후보 비교 및 근거 선택 개선

- **현재 문제:** T1.5는 추가 검색으로 보완하는 항목마다 검색 결과의 첫 번째 후보 하나만 인용으로 붙입니다.
- **개선 방향:** 상위 **2~3개 검색 후보**를 비교하여 확인하려는 **금액·날짜·조건**이 실제로 담긴 근거를 선택하도록 보완합니다.
- **목적:** 첫 번째 후보에는 필요한 정보가 없더라도 뒤쪽 후보에 해당 정보가 있으면 적절한 근거를 인용할 수 있도록 합니다.

### 보완 2. T3 과거 사업 데이터 정리

- **현재 문제:** 검색 대상 **112개 사업** 중 일부에서 **목차·계약 조항**이 실제 사업 내용으로 잘못 추출되어 벡터화되었습니다.
- **개선 방향:**
  - 프로그램 규칙으로 잘못된 구간을 탐지하고 재추출하는 방법을 검토합니다.
  - 필요하면 AI가 원문에서 실제 사업 내용을 선택하도록 하는 방법을 검토합니다.
  - 판단이 어려운 자료는 사람이 확인·수정할 수 있도록 합니다.
- **후속 작업:** 수정한 사업 본문을 **다시 벡터화**하고 저장된 **검색 데이터를 갱신**합니다.

### 2.2. 추가 보완 검토 — OCR 기반 PDF 처리

- 기존 `pdfreader`, `pdfplumber` 방식에서 나아가, **PDF 자체를 OCR로 읽고 요약한 내용을 LLM에 전달**하는 방향의 코드 수정이 필요합니다.
- OCR 적용 범위 및 구현 방식은 기존 추출 방식과 비교·검토하여 결정합니다.

### 2.4. 추가로 확인된 데이터 문제와 예외처리

**① 통합정보시스템 사업의 계약기간 불일치**

- RFP에는 **2027년**, 공고문에는 **2026년**으로 서로 다르게 기재되어 있습니다.
- 문서 간 기간 불일치 사례로 별도 확인이 필요합니다.

**② 상수도관 사업금액의 VAT 표기 차이 및 예외처리**

- RFP 금액: **107,000,000원(VAT 별도)**
- 공고문 금액: **117,700,000원(VAT 포함)**
- 두 금액은 **부가세 10%를 적용하면 일치**하므로 금액 자체가 충돌하는 것은 아닙니다.
- **추가 보완 사항: `VAT 포함`으로 표기된 금액은 예외처리하여, `VAT 별도` 금액과 단순 숫자 비교만으로 충돌이라고 판정하지 않도록 합니다.** VAT 포함 여부를 먼저 확인하고 비교 기준을 맞춘 뒤 실제 불일치인지 판단합니다.

### 2.5. 공고함 선별 기준 40억 원의 VAT 포함 여부 명확화

- **현재 문제:** 공고함에서 사업금액 **40억 원 이상**을 선별하는 기준을 사용하지만, 이 기준이 **VAT 포함 금액**인지 **VAT 별도 금액**인지 명확히 정의할 필요가 있습니다.
- **보완 방향:** 팀에서 선별 기준의 **VAT 포함 여부를 명시적으로 결정**하고, 공고문에 표시된 사업금액의 VAT 포함 여부를 확인한 다음 **같은 기준으로 환산·비교**하도록 처리합니다.
- **수정·확인 위치:** `config/notice_filter.yaml`의 `min_amount_krw` 설정 및 `notice_filter.py`의 사업금액 비교 로직. 공고함 화면에도 **`40억 원 이상 (VAT 포함)`** 또는 **`40억 원 이상 (VAT 별도)`**처럼 결정된 기준을 표시합니다.
- **예외처리:** VAT 포함 여부가 확인되지 않는 공고는 임의로 포함/별도 처리하지 않고 **`확인 필요`**로 구분하여 잘못된 공고 선별을 방지합니다.
- **진행 상태:** **VAT 포함 여부 결정 및 코드·화면 반영 필요**. 현재 어떤 기준으로 동작하는지는 별도 확인해야 합니다.

## 3. 이주안 — LangGraph 기반 Agentic Workflow 보완

### 보완 1. 최종 보고서 생성(T4)까지 Workflow 확장

- **현재:** LangGraph가 **T1 요구사항 분석 → T1.5 검증 → T2 회사 역량 분석 → T3 유사사업 조사**까지 실행된 후 종료됩니다.
- **보완:** 기존 Agent 4의 보고서 생성 기능을 LangGraph의 **`T4 Report Writer` Node**로 연결합니다.
- **추가:** 최종 보고서에 **사업금액·참가자격·회사 역량·유사사업 분석 결과와 원문 근거**가 반영되었는지 검증하는 Node를 추가합니다.
- **기대 결과:** RAG 검색부터 최종 입찰 검토 보고서 작성까지 하나의 LangGraph Workflow에서 관리합니다.

### 보완 2. Human-in-the-Loop 실행 재개 기능 개선

- **현재:** 검증 실패 시 `human_review` Node에서 확인 필요 상태를 기록하고 실행을 종료합니다. 담당자 승인 후 승인 정보를 전달해 그래프를 다시 실행합니다.
- **보완:** LangGraph의 **`interrupt()`와 Checkpointer**를 적용해 담당자 확인 시점에 실행을 일시 중지하도록 개선합니다.
- **추가:** 담당자의 **승인·수정·반려** 결과를 State에 기록하고 **`Command(resume=...)`**을 통해 중단된 작업을 이어서 실행합니다.
- **기대 결과:** 처음부터 분석을 다시 수행하지 않고 담당자 검토 이후 기존 작업을 이어갑니다.

### 보완 3. Agent 2·3 분석 결과에 대한 Evaluation 추가

- **현재:** T1.5에서 사업금액·참가자격·기간을 검증하지만 Agent 2·3의 후속 분석 결과를 별도로 검증하는 과정은 제한적입니다.
- **보완:** Agent 2의 **회사 역량 판단**과 Agent 3의 **유사사업 검색 결과**에 대한 검증 Node를 추가합니다.
- **추가:** 회사의 **실제 수행실적·법인 일치 여부**, 유사사업의 **원문 근거·낙찰정보 연결 여부**를 확인하고 근거 부족 시 **`확인 필요`** 처리합니다.
- **기대 결과:** 후속 Agent의 근거 없는 판단이 최종 보고서로 전달되는 문제를 줄입니다.

### 보완 4. 재검색·재분석 Conditional Routing 개선

- **현재:** T1.5 검증 결과가 불충분하면 RAG 추가 검색을 수행하고, 반복 실패나 정보 충돌 시 Human Review로 이동합니다.
- **보완:** 검증 실패 원인에 따라 재검색 대상과 재실행할 Agent를 구분합니다.
- **분기 조건:**
  1. **원문 근거 부족** → 해당 항목 RAG 재검색
  2. **Agent의 원문 해석 오류** → 해당 Agent 재분석
  3. **서로 다른 문서의 정보 충돌** → 담당자 확인
  4. **재검색 횟수 초과** → Human Review
- **기대 결과:** 모든 오류를 동일하게 처리하지 않고 원인별로 필요한 작업만 재실행합니다.

### 보완 5. LangGraph State 및 공고별 실행 정보 관리 강화

- **현재:** `BidReviewState`에 공고번호, RFP 분석 결과, 검증 상태, 추가 검색 횟수, 회사 역량 및 유사사업 분석 결과 등을 저장합니다.
- **보완:** **공고 ID·문서 버전·실행 ID**를 기준으로 각 공고의 분석 상태와 검색 근거를 명확하게 분리합니다.
- **추가:** Agent별 실행 결과, Evaluation 오류 사유, 재검색 이력, 담당자 수정 내역을 State 및 별도 실행 기록에 저장합니다.
- **기대 결과:** 서로 다른 공고의 정보 혼동을 줄이고 오류가 발생한 단계를 추적할 수 있도록 합니다.

### 보완 6. Conditional Routing 및 Workflow 테스트 강화

- **현재:** LangGraph의 State·Node·Conditional Routing 및 재검색 경로는 구현되어 있으나 다양한 사례에 대한 통합 검증이 추가로 필요합니다.
- **보완:** **정상 처리, RAG 근거 부족, 원문 정보 충돌, 재검색 횟수 초과, 담당자 승인** 등 **최소 5개 상황**을 대상으로 Workflow를 테스트합니다.
- **추가:** 각 테스트에서 실제 실행된 **Node 순서·State 변화·조건부 분기 결과·최종 처리 상태**를 로그로 저장합니다.
- **기대 결과:** 업무 상황에 따라 서로 다른 경로로 작동하는 LangGraph Workflow임을 검증합니다.

### 보완 7. 순차·병렬 Workflow 구현 및 성능 비교

- **현재:** LangGraph의 T1 → T1.5 → T2 → T3 흐름을 **순차 실행 기준선**으로 사용합니다.
- **보완:** 앞 단계의 결과가 필요한 **T1·T1.5는 순차로 유지**하되, T1.5 검증이 끝난 후 서로 독립적으로 수행 가능한 **T2 회사 역량 분석과 T3 유사사업 조사**를 **병렬 실행**하도록 Workflow를 변경합니다. 두 작업이 모두 끝나면 T4 보고서 생성 단계에서 결과를 합칩니다.
- **비교 방법:** 동일한 공고·입력 문서·AI 모델·설정을 사용해 **순차 구조와 병렬 구조를 각각 실행**하고, 실행별 **전체 처리 시간(초)** 및 **입력·출력·총 토큰 사용량**을 기록합니다. 최소 5개 사례로 비교하며, 반복 실행한 결과의 평균도 제시합니다.
- **평가 항목:** 실행 시간 단축 여부, 총 토큰 사용량 변화, 최종 보고서의 내용·검증 결과가 동일하게 유지되는지 확인합니다.
- **기대 결과:** 병렬 처리의 실제 효율을 수치로 비교하고, **병렬화가 시간을 단축할 수는 있지만 토큰 사용량을 반드시 줄이는 것은 아니라는 점**을 결과로 검증합니다.
- **협업:** **이주안**이 LangGraph 실행 구조 및 성능 측정 로그를 구현하고, **송하연·인진은**이 동일한 테스트 데이터와 결과 정확성 검증을 지원합니다.

## 4. 팀 전체 작업 연결 및 협의 사항

| 진행 순서 | 담당자 | 연결 내용 |
|---|---|---|
| T1: PDF에서 핵심정보 추출 및 검색 | **송하연** | 공동도급·금액·날짜 등 추출 정확도와 검색 데이터 품질 확보 |
| T1.5: 검색 근거 비교·선택 | **인진은** | 상위 검색 후보 비교 및 적합한 근거 선택 |
| T2·T3: 후속 분석·검증 | **인진은 / 이주안** | 정제된 과거사업 데이터 제공, 후속 Agent 결과 검증 |
| T4: 보고서 생성 및 검증 | **이주안** | 검증된 자료를 최종 Go/No-Go 보고서에 연결 |
| 전체 실행 | **팀 공동** | Human Review·오류별 분기·최소 5개 시나리오 검증 |
| 순차·병렬 성능 비교 | **이주안 주도 / 팀 공동** | T2·T3 병렬 실행 전후 시간·토큰 사용량 측정 및 결과 정확성 비교 |

**협의할 사항**

1. `rag/workflow.py`에서 **인진은의 T1.5 근거 선택 변경**과 **이주안의 Node·State·Routing 변경**이 충돌하지 않도록 수정 범위를 조율합니다.
2. **송하연의 VAT 포함 예외처리 기준**이 T1.5 검증·문서 충돌 분기에 반영되도록 공유합니다. VAT 기준 차이는 실제 금액 충돌과 구분합니다.
   - **공고함의 40억 원 선별 기준**도 VAT 포함/별도 중 어느 기준인지 명시하고, `notice_filter.yaml`·선별 로직·화면 안내에 동일하게 반영합니다.
3. **통합정보시스템 계약기간의 2026년/2027년 불일치**는 실제 원문과 문서 판본을 확인한 뒤 충돌 검증 사례로 활용합니다.
4. **정제된 T3 사업 본문과 재생성한 검색 인덱스**가 이주안의 후속 검증 단계에서 사용되도록 연결합니다.
5. **순차·병렬 비교**에서 같은 입력·모델·측정 기준을 적용하고, 실행 시간뿐 아니라 토큰 사용량과 분석 정확성도 함께 확인합니다.
