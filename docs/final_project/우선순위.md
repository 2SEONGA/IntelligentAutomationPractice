## 프로젝트 방향 확정

기존 공공 SI 입찰 검토 시스템을 확장한다. T1이 추출한 **사업금액·참가자격·사업기간 등 핵심 정보**를 후속 분석에 넘기기 전에 원문 근거와 대조하는 **T1.5 증거 검증 단계**를 둔다. 기존 업무 맥락은 입찰 검토 전체로 유지하되, 검증 대상별 깊이를 확보하도록 각 항목의 판정 기준·근거·예외·실패 경로를 별도로 설계한다.

검증 대상은 다음과 같이 구체화한다.

- **사업금액:** 예산/추정가격 구분, VAT, 총액/연차별 금액, 금액 변환, 문서 간 일치 여부
- **참가자격:** 자격 조건의 주체·조건·예외·공동수급/제한 조건, 확인 근거와 누락 여부
- **기간·기한:** 계약 수행기간, 제안서/입찰 마감일, 일정 종류의 구분, 문서 간 충돌 및 날짜 해석

각 범주는 필요한 원문 근거를 RAG로 찾아 검증하고, 불충분·충돌 상태에서는 추가 검색 또는 담당자 검토로 분기한다. 3개 범주를 모두 깊이 있게 다루기 위해 우선 정형 판정 규칙과 검증 사례를 만들고, 구현 범위는 팀의 일정·데이터 확인 후 MVP 단위로 조정한다.

## 실행 원칙

- 순위 작업 하나가 끝날 때마다 `tasks/`에 해당 작업의 상세 기록을 작성한다.
- 구현 마일스톤이 끝날 때마다 `implementation/M*.md` 상단에 `## 요약`(한 일·결과·남은 일)을 쓰고, 같은 내용을 이 문서의 `마일스톤별 작업 정리`에 추가하며 상태 표 2개를 갱신한다.
- 상세 기록에는 작업 목표, 조사·결정 내용, 근거 파일, 미해결 항목, 완료 기준, 다음 순위를 포함한다.
- 사용자 의견이 필요한 선택은 가능한 선택지와 영향 범위를 제시하고, 답을 받기 전에는 해당 선택에 의존하는 설계를 확정하지 않는다.
- 코드 변경은 데이터·검증·그래프 설계가 합의된 뒤 최소 시연 범위부터 진행한다.
- RAG와 LangGraph는 과제 필수 요건이다. CrewAI의 유지 여부는 각 기술이 맡을 역할과 구현 복잡도를 비교해 결정한다.

### 마일스톤별 작업 정리

각 마일스톤의 한 일·결과·남은 일을 간략히 정리한다. 마일스톤이 끝날 때마다 이 목록에 항목을 추가하고, 상세 내용은 링크한 문서에 남긴다.

#### M1 RAG 코퍼스와 로컬 기초 검색

상태: 완료 · 문서: [`M1_RAG_코퍼스_기초검색.md`](implementation/M1_RAG_코퍼스_기초검색.md)

- **한 일:** 원본 RFP 3건을 페이지·절·표 단위로 분할하고 연락처 행을 제거해 SQLite FTS5 키워드 검색 색인을 구축했다.
- **결과:** 848 chunk(본문 813 + 나라장터 metadata 35), 페이지·공고번호 인용형 검색 CLI 동작.
- **남은 일:** 의미 검색은 M4에서 추가됨, 공고 첨부 판본 대조는 M18에서 RFP 3건 바이트 동일 확인, OCR·개인정보 추가 점검.

#### M2 T1.5 핵심정보 검증기

- **결과:** 금액 단위·VAT·범위, 자격 조건 구조, 날짜 정규화·충돌 감지 체크와 citation을 기록. 3건 기준선 JSON 생성.

#### M4 의미 검색 (OpenAI 임베딩)

상태: 완료. RFP·공고문 코퍼스 의미 검색과 T1.5 보조 검색 연결. Agent 2(회사 자료)·Agent 3(과거 RFP) 의미 검색은 후속. · 문서: [`M4_의미검색_선택대기.md`](implementation/M4_의미검색_선택대기.md)

- **한 일:** 사용자 결정(2026-11-17, API 방식)에 따라 OpenAI `text-embedding-3-small`로 RAG 코퍼스 1,024 chunk를 임베딩했다. 의미 검색 CLI를 만들고, T1.5 추가 검색에서 키워드가 아무것도 못 찾은 질의에만 의미 검색을 보조로 붙였다.
- **결과:** 원문과 다른 표현의 질의("부가세 포함한 전체 예산 금액", "제안 서류를 언제까지 내야 하나")는 키워드 검색 결과가 0건이었지만 의미 검색은 관련 쪽을 찾았다. 세 공고 실행에서 보조 검색이 실제로 사용됐다. 의미 검색으로 붙은 근거는 모두 담당자 검토로 남고 자동 확정하지 않는다. 테스트 16개 파일, 웹 빌드 통과.
- **남은 일:** 회사 자료 RAG(M21)와 과거 RFP(Agent 3, M23)에 적용했다. 임계값은 정답 평가로 재조정 필요. 임계값 0.40은 표본 기준이라 정답 라벨 평가셋으로 다시 맞춰야 한다. LlamaIndex는 쓰지 않았다(아래 결정).

## 대면 회의 후 추가 구현 방향 (2026-11-16)

회의에서 논의한 RAG 확장은 다음 순서로 진행한다.

1. **Agent 2 — 자사 역량·수행실적 RAG**: `data/company/company`의 공개 근거 자료를 기반으로 T1이 추출한 요구사항별 관련 기술·사업·실적을 검색한다. 이 파일에는 현재 11개 records, 8개 sources와 미확인 증빙 목록이 있다. 검색 결과는 적합성 확정이 아니라 원문 증빙을 확인할 후보이며, 수행 법인은 ㈜아이티센엔텍으로 한정한다. 그룹사 실적을 대상 법인 실적으로 혼동하지 않도록 entity 경계를 보존한다.
2. **Agent 3 — 과거 공공사업/RFP 의미 검색**: 과거 RFP 원문 또는 사업 범위 자료를 사업별로 수집하고, 사업 목적·수행 범위·기술요건을 검색해 신규 사업과 비교한다. 낙찰기업·낙찰금액·발주기관은 연결 근거가 확보된 경우에만 제시한다. 사전 자료 검색은 나라장터 실시간 조회와 독립적으로 실행한다.
3. **검증·업무흐름 연결**: 검색 결과마다 문서/출처/페이지와 공통점·차이점을 남기고, 근거 부족·충돌·법인 귀속 불확실 시 담당자 검토로 보낸다. RAG 유사도만으로 실적 자격, 사업 유사성 또는 참여 결정을 자동 확정하지 않는다.

회의에서 제안된 10억 기준 추가는 채택하지 않는다. 내부 정책 확인 전까지 공고 필터와 체크리스트의 현행 40억·100억 기준을 유지하고, 기준 근처의 자동 제외 여부도 현행 기준을 임의 변경하지 않는다.

구현 전에 확인할 사항: `data/company/company`의 11개 공개 자료 각각의 출처·발행 시점·대상 법인·증빙 한계, 과거 RFP 자료의 수집 가능 범위와 낙찰 데이터 연결키, 벡터 검색을 위한 임베딩 실행 방식. 현 RAG는 SQLite FTS 키워드 검색이므로 Agent 2/3 의미 검색을 구현하려면 M4의 임베딩/벡터 저장 선택을 다시 구체화해야 한다.

상세 의사결정 기록: `implementation/M9_대면회의_RAG확장_결정.md`.

RunResult 결과 화면에는 `핵심정보 검증`과 `Go/No-Go 체크리스트`가 각각 별도 탭으로 있다. 체크리스트 탭은 1단계 참가 가능 여부(탈락요건), 2단계 매력도·수주 가능성 점수, 판단 근거 및 원문 페이지 링크를 보여주며 사업기획 담당자가 현재 점수/판정을 수정할 수 있다. 이는 T1.5 금액·참가자격·기간의 증거 검증과 목적/결과가 다르므로 별도 화면·기록으로 유지한다. 세 최신 웹 실행은 모두 체크리스트 9개 항목이 있고 요약 권고는 `보류`다.

### 직원별 로그인 및 역할 검증 (후속 요구사항, 미구현)

현재 시작 화면의 역할 선택은 테스트용이며, 선택값은 브라우저 `sessionStorage`와 요청 헤더 `X-Role`에 실린다. 서버는 role 값만으로 인가하므로 직원 신원을 검증하지 않는다. 실제 사용 전에는 직원별 사내 계정 인증과 서버 측 역할 매핑으로 교체해야 한다.

후속 설계에서 필요한 사항:

- 사내 ID/비밀번호 인증 또는 사내 SSO/디렉터리 연동 방식 확정 (사내 인증 제공자가 있으면 계정 비밀번호를 앱에서 직접 보관하지 않는 연동 방식을 우선 검토)
- 직원 계정과 역할(사업기획 담당자/사업본부장 등)의 관리·부여·회수 정책
- 클라이언트가 보낸 역할 문자열을 권한 근거로 사용하지 않고, 서버가 검증된 로그인 세션의 계정과 역할로 매 요청을 인가
- 감사 이력에 직원 식별자, 검증된 역할, 시각, 동작 및 사유 기록
- 로그아웃·세션 만료와 계정 비활성화 처리

인증 시스템/담당 조직/테스트 계정이 정해지지 않아 구현은 시작하지 않는다. 과제 시연의 역할 선택을 실제 보안 인증으로 표현하지 않는다. 사내 인증 방식과 역할 정책은 실제 연동 설계 전에 담당자 의견을 확인한다.
