## 1. macOS 실행 환경

`실행안내.md`는 Windows 기준(`setup.ps1`, `.venv\Scripts`)이라 macOS에서는 다음처럼 실행했다.

```bash
python3.12 -m venv .venv
.venv/bin/pip install -e .
.venv/bin/python run.py --mode offline --output outputs/offline --verbose --save-intermediate
```

결과는 PDF 3개 모두 처리, 오류 0개였다. 세 건 모두 `보류`로 나왔는데, 공고문이 없어서이며 정상이다.

## 2. Agent 설정의 YAML 전환

### 왜 바꿨나

- Agent 프롬프트, 회사 정책, 판단 키워드가 Python 코드 안에 문자열로 흩어져 있었다.
- 그래서 프롬프트 한 줄을 고치려 해도 코드를 열어 f-string 문법(`{{ }}` 이스케이프 등)을 맞춰야 했다.
- 이제는 `config/` 폴더의 YAML만 고치면 된다. CrewAI 공식 프로젝트 구조(`config/agents.yaml`, `config/tasks.yaml`)와도 같다.

### 무엇을 어디로 옮겼나

| 새 위치 | 내용 | 이전 위치 |
|---|---|---|
| `config/agents.yaml` (신규) | Agent 4개의 role·goal·backstory | `crew.py` Agent 생성부 |
| `config/tasks.yaml` (신규) | Task 4개의 description·expected_output | `crew.py` Task 생성부 |
| `config/policy.yaml` (신규) | 분석 대상 법인명, 보고서 표시 법인명, 나라장터 검색어, 공통 검토 원칙 9개, 샘플 데이터 안내문 | `policy.py`, `agent04_report.py` |
| `config/settings.yaml` `rfp:` 아래 (추가) | 요구사항 분류 키워드(`category_keywords`), 참가자격·인력·제출 용어, 사업명·기관명 제외어 | `agent01_rfp.py` 상수 |
| `config/settings.yaml` `capability:` (추가) | 실적 판단 용어(`performance_terms`) | `agent02_match.py` |
| `config/settings.yaml` `pdf_evidence:` (추가) | live Agent PDF 근거 도구의 페이지·글자 수 한도 | `crew.py` 상수 |

### 자리표시자 두 종류

YAML 문자열 안에는 자리표시자가 두 종류 있고, 채우는 시점이 다르다.

| 모양 | 채우는 시점 | 예 |
|---|---|---|
| `$이름` | YAML을 읽을 때, `policy.yaml` 값으로 | `$target_legal_entity`, `$common_agent_rules`, `$g2b_search_terms` |
| `{이름}` | CrewAI 실행 시, 분석 결과로 | `{notice_summary}`, `{rfp_summary}`, `{company_summary}`, `{market_summary}` |

- `$` 쪽은 표준 라이브러리 `string.Template`의 엄격 모드로 채운다(`policy.render_prompt`).
- 그래서 변수명에 오타가 있으면 실행 즉시 `KeyError`가 난다. 틀린 프롬프트가 조용히 LLM에 전달되지 않는다.
- `{}` 쪽은 지우면 Agent가 입력을 받지 못하므로 그대로 둔다.

### 코드에 남긴 것

| 항목 | 남긴 이유 |
|---|---|
| 요구사항 ID·날짜 정규식 | YAML로 옮기면 이스케이프 때문에 깨지기 쉽다. |
| 상태값(`충족`/`부분 충족`/`미충족`/`확인 필요`) | Pydantic 모델의 허용값이라 코드와 함께 바뀌어야 한다. |
| Task 이름, 산출물 경로(`debug/01_...json`) | `models.py`가 이 경로로 검증한다. |

### 코드 쪽 변경

- `settings.py`: `load_config(name)`을 추가했다. `config/<name>.yaml`을 읽는다.
- `policy.py`: `policy.yaml`을 읽어 기존과 같은 상수 이름으로 내보낸다. `render_prompt()`를 추가했다.
- `crew.py`: Agent·Task 생성부의 프롬프트 문자열(77줄)을 YAML 참조로 바꿨다.
- `agent01_rfp.py`, `agent02_match.py`, `agent04_report.py`: 상수 이름은 그대로 두고 값만 YAML에서 읽는다.
- 키워드는 항상 기본 `config/settings.yaml`에서 읽는다. 다른 설정 파일을 지정해 실행해도 키워드는 바뀌지 않는다. 코드에 `ponytail:` 주석으로 표시했다.

### 동작이 같다는 확인

- YAML로 만든 프롬프트 8종(Agent 4개, Task 4개)이 기존 코드 문자열과 글자 단위로 같다.
- 키워드·정책 상수 값이 같다.
- offline 재실행 결과 21개 파일이 타임스탬프 외 차이 0개다.

### YAML을 고칠 때

1. `config/` 안의 해당 YAML을 고친다.
2. `.venv/bin/python tests/test_config.py`를 실행해 `config OK`가 나오는지 확인한다.
3. 검사 항목: 변수명 오타, 빠진 CrewAI 입력, 공통 원칙 포함 여부, 키워드 범주별 가중치 존재, 체크리스트 형식.

## 3. Go/No-Go 체크리스트

자세한 해설은 [go_no_go_checklist.md](go_no_go_checklist.md)에 있다. 판단 기준은 `config/checklist.yaml`에 있다.

### 근거 데이터

- 2023-10 ~ 2026-10 나라장터 용역 낙찰 351,025건을 받았다.
- 그중 아이티센 그룹 낙찰은 93건이다. 그룹사 여부는 사업자번호로 확인했다.
- 판단 기준은 그중 ㈜아이티센엔텍(구 쌍용정보통신) 67건에서 뽑았다.
- 데이터: `data/market/itcen_group_awards_3y.json` / 재수집: `scripts/collect_g2b_awards.py`

### 체크리스트 구성

- **1단계, 참가 가능 여부 4개 항목:** 참가자격, 대기업 참여제한, 공동수급·지역, 필수 인증·인력.
  - 하나라도 미충족이면 No-Go, 확인 필요가 있으면 보류다.
- **2단계, 점수 5개 항목(10점 만점):** 규모, 사업 유형, 발주기관, 후속 사업 여부, 예상 경쟁.
  - 6점 이상이면 Go 권고, 4~5점이면 사업본부장 검토, 3점 이하면 No-Go 권고다.
  - 과거 낙찰 67건에 적용하면 51건(76%)이 Go로 나온다.

### 한계

- 내부 판단 기록이 아니라 "참여해서 이긴 공고"를 Go로 본 근사치다.
- 진 입찰과 컨소시엄 구성원으로 참여한 사업은 데이터에 없다.
- 기준을 만든 데이터와 검증한 데이터가 같아서(표본 내 검증), 실제 판단 결과가 쌓이면 다시 맞춰야 한다.

### 참고

- 내부 금액 기준(`minimum_project_amount_krw`, 10억)은 실제 낙찰 패턴(40억 이상)보다 낮다. 조정을 검토할 필요가 있다.
- 샘플 RFP 3건(1.07억, 10.7억, 3억)은 모두 과거 낙찰 범위보다 작다.

## 4. 나라장터 조회 버그 수정

live 모드에서 시장조사(`market.allow_live_lookup: true`)를 켜면 쓰이는 코드다. 버그 네 개가 서로를 가리고 있었다.

| # | 문제 | 증상 | 수정 |
|---|---|---|---|
| 1 | API가 `items`를 리스트로 주는데, 코드는 딕셔너리 형태만 읽었다 | 모든 조회가 항상 0건 | 리스트와 딕셔너리 형태 모두 처리 |
| 2 | 오류 응답(`nkoneps.com.response.ResponseError` 봉투)을 성공으로 처리했다 | 실패가 "0건"으로 보임 | 오류 봉투를 인식해 `G2BApiError` 발생 |
| 3 | 조회 기간을 1,095일 한 번에 요청했는데, API 한도는 1개월이다 | 항상 `07 입력범위값 초과` (2번 때문에 안 보임) | 최신순 31일 구간으로 나눠 `max_results`까지 조회 |
| 4 | 회사명 필터(`sucsfbidderNm`)를 API가 지원하지 않는다 | 다른 회사 낙찰이 섞여 들어옴 | 수집해 둔 그룹 낙찰 데이터에서 낙찰자명으로 거름 (`market.company_awards_file`) |

함께 고친 것:

- 낙찰자 필드명을 실제 API 필드로 바꿨다. 낙찰 목록은 `bidwinnrNm`, 개찰결과는 `opengCorpInfo`의 첫 항목이다.
- 개찰일 필드에 `rlOpengDt`를 추가했다.
- 어떤 Agent도 쓰지 않던 `g2b_company_award_search` 도구를 지웠다. 4번 문제로 잘못된 결과를 내는 도구였다.

확인 결과:

- 실제 API로 3년치 유사사업 '나이스'를 검색하면 20건이 낙찰자와 함께 나온다. 수정 전에는 0건이었다.
- 회사 검색은 아이티센엔텍 39건, 쌍용정보통신 29건이 나온다.
- 출처 URL에 API 키가 노출되지 않는다.
- offline 결과는 수정 전과 같다(30개 파일, 차이 0개).
- 회귀 테스트: `.venv/bin/python tests/test_g2b.py` (네트워크 없이 실행)

참고: 유사사업 검색은 RFP 1건당 나라장터를 최대 36번 호출한다. 결과가 `max_results`(20건)만큼 모이면 멈춘다.

## 5. 웹페이지

설계: [superpowers/specs/2026-10-27-bid-review-web-design.md](superpowers/specs/2026-10-27-bid-review-web-design.md) / 구현 계획: [superpowers/plans/2026-10-27-bid-review-web.md](superpowers/plans/2026-10-27-bid-review-web.md)

### 구조

```
브라우저 (React + Vite + 원티드 Montage 4.1.3)
   │  fetch / SSE
FastAPI (127.0.0.1:8000) ── 하위 프로세스 ──▶ run.py (기존 CLI) ──▶ outputs/web/<실행시각>/
   └─ 체크리스트 판정 · 결정 저장
```

- 웹 서버는 기존 CLI를 그대로 실행하고, 출력 줄을 실시간으로 화면에 보낸다. 파이프라인 결과는 CLI로 실행한 것과 같다.
- `crew.py`에 진행 표시 줄 `[STAGE] <agent1~4> <start|done|skip>`을 추가했다. `--verbose`와 상관없이 항상 출력되며, 화면은 이 줄로 진행 막대를 갱신한다. offline 결과 파일은 이전과 같다(30개 파일 차이 0).
- 체크리스트 자동 판정(`src/bid_review/checklist.py`):
  - 근거가 없으면 1단계는 `확인 필요`, 2단계는 `미정`으로 둔다.
  - K2(대기업 참여제한)와 K3(공동수급)는 담당자가 확인하기 전까지 늘 `확인 필요`라서, 체크리스트 권고는 대개 보류로 시작한다.
- 화면은 보고서 권고(Agent 4)와 체크리스트 권고를 따로 보여주고, 둘이 다르면 경고한다.
- 사업본부장 결정은 사유가 필수다. 바꾸면 이전 결정이 이력으로 남는다.

### 검증 결과

- **자동 검사:** 백엔드 테스트 7개 파일, 프론트엔드 테스트 9개, 빌드 모두 통과
- **기존 결과 비교:** offline 결과 파일 30개가 웹 기능 추가 전과 동일
- **브라우저 시연:**
  - PDF 3개 모두 웹 업로드 → 진행 → 결과까지 확인
  - 실행 중 새로고침하면 진행 화면으로 복귀
  - Agent 단계가 0.6초 간격으로 순서대로 표시
  - 체크리스트 수정, 결정 저장·이력, 내려받기 동작
- **live 모드:** 실행하지 않음(OpenAI 비용). live의 진행 표시 순서는 단위 테스트로만 확인했다.

### 최종 리뷰와 수정

별도 검토자의 결론은 "고친 뒤 마무리 가능"이었다(치명적 문제 0건). 지적 7건을 고쳤고, 각각 실패하는 테스트를 먼저 만든 뒤 통과시켰다.

| 지적 | 수정 |
|---|---|
| 미정 항목이 남아도 "No-Go 권고"가 확정처럼 표시됨 | 미정 항목 때문에 권고 구간이 바뀔 수 있으면 **보류**로 두고, 점수를 범위(예: 1~7점)로 표시 |
| 웹 실행 결과의 offline/live 구분이 사라짐 | `upload.json`의 실행 방식을 읽어 "offline · 웹"처럼 표시 |
| 연결이 잠깐 끊겨도 "중단"으로 표시됨 | 서버가 응답하면 최대 3번 처음부터 다시 연결(재연결 판단 로직만 테스트, 실제 끊김은 미재현) |
| 다른 사이트가 이 서버에 요청을 보내 유료 live 실행을 시작할 수 있음 | Host·Origin 검사로 이 앱 화면에서 온 요청만 허용 |
| 사업명이 없으면 S4가 근거 없이 0점 | 미정으로 표시 |
| 체크리스트 결과를 내려받을 수 없음(스펙 3.5) | "체크리스트 결과" 다운로드 추가(평가 전체) |
| 옛 보고서의 체크리스트 근거 문구가 오해를 줌 | 체크리스트 탭에 "자동 판정이 제한된 옛 보고서" 경고 추가 |

### 구현하면서 판단해서 정한 것

- **git:** 저장소가 아니라서 커밋하지 않았다. 진행 기록은 `.superpowers/sdd/2026-10-27-bid-review-web/progress.md`에 남겼다.
- **한글 파일명:** 기존 결과 파일명에 NFC/NFD 두 방식이 섞여 있어, 모든 파일명을 NFC로 맞춰 비교한다.
- **사업명 표시:** 보고서 JSON에 사업명이 없어서, 목록에는 올린 파일명이나 폴더명을 쓴다.
- **고정 버전:** Montage 4.1.3, Vite 8.3.4, TypeScript 5.9.3(7.x는 새 메이저라 제외), FastAPI 0.143.0. 모두 공개 2주 이상 지난 버전이다.
- **화면 세부:**
  - 파일 카드의 쪽수 표시는 뺐다(브라우저에서 PDF를 읽어야 해서).
  - 저장 알림은 Toast 대신 카드 안 메시지로 보여준다.
  - "다시 시도" 때 고른 파일을 유지한다.
- **계획에 없던 처리:**
  - 내부 오류가 나도 진행 화면이 멈추지 않고 오류로 끝난다.
  - live 키가 없으면 서버도 live 요청을 거부한다.
- **확인 기준 수정:** 계획의 "K2·K3만 충족하면 통과"는 CDW에서 맞지 않아 K1~K4 전부 충족으로 확인했다.
- **offline 진행 표시:** offline은 Agent 2·3이 실제로 차례로 실행되므로 화면도 차례로 보인다. 동시 실행 모습은 live에서만 보인다.

### 미뤄 둔 작은 문제

- 실행 프로그램을 띄우는 단계에서 오류가 나면, 서버를 다시 켜기 전까지 새 실행이 막힌다(`jobs.py` `start`).
- 로그 가리기가 `.env`의 모든 값에 적용된다. 그래서 모델 이름도 `***`로 보이고, 셸에서만 설정한 키는 가려지지 않는다.
- 업로드 크기를 파일을 다 읽은 뒤 검사한다. 오류 문구에 "입찰공고문**는**" 조사 오류가 있다.
- 실행이 끝난 뒤 다른 화면에 있으면 왼쪽 "진행 중" 칸이 늦게 사라진다.
- live에서 "보고서 작성 시작" 표시가 두 번 들어올 수 있다(화면에는 영향 없음).
- live 실패 메시지가 웹에서 열 수 없는 `crew_live_error.txt`를 가리킨다.

## 6. 웹페이지 v2 — 공고 수집 · 대시보드 · 역할별 결재

3·4·5주차 과제 PDF의 To-Be 흐름(① 공고 수집 → ② 규칙 필터 → ②-1 담당자 확인 → ③ 문서 확보 → Agent 1~4 → ⑧ 본부장 결재 → ⑨ 이력)을 웹에서 돌리도록 재구성했다.

- 설계: [superpowers/specs/2026-10-27-bid-review-web-v2-design.md](superpowers/specs/2026-10-27-bid-review-web-v2-design.md)
- 구현 계획: [superpowers/plans/2026-10-27-bid-review-web-v2.md](superpowers/plans/2026-10-27-bid-review-web-v2.md)

### 무엇이 바뀌었나

**메뉴와 역할**
- 왼쪽 메뉴는 6개다: 대시보드 / 공고함 / 검토 / 결재함 / 의사결정 이력 / 판단 기준. v1 화면(업로드·진행·결과)은 "검토" 메뉴로 옮겼다.
- 상단에서 역할(사업기획 담당자 / 사업본부장)을 바꾼다.
  - 화면 버튼과 서버 API가 같은 권한 표를 따른다. 역할 헤더가 없거나 틀리면 상태 변경 요청은 403이다.
  - 시연용 구분이며 보안 인증은 아니다.

**공고 수집과 필터**
- 나라장터 입찰공고 API(`G2B_BID_NOTICE_KEY`)로 공고를 수집한다.
- 규칙 필터(`config/notice_filter.yaml`): 40억 이상, ICT 분류, 마감 3일 넘게 남음, 수의계약 제외. 제한경쟁·지역제한·물품분류제한·입찰참가제한은 "담당자 확인 필요"로 보낸다.
- 업종제한(83%가 해당)과 공동도급 의무지역(전부 빈 값)은 실제 응답 271건을 보고 판정에서 뺐다. 근거는 YAML 주석에 적었다.

**문서 확보**
- 첨부 PDF를 자동으로 받아 공고문과 RFP로 나눈다. 실제 이름에 쓰이는 "공고서"·"재공고서"도 공고문으로 인식한다.
- RFP PDF가 없으면 업로드 화면으로 넘어가고, 같은 폴더에서 실행한다.

**결재 흐름**
- 검토 완료 → 결재 대기 → 결정 완료. 반려하면 보완 요청으로 돌아간다(사유와 요청 방식 필수).
- 담당자는 보완 후 다시 올리거나 다시 실행한다.
- 결재 대기·결정 완료 중에는 체크리스트가 잠긴다.
- 상태와 이력은 검토 건 폴더의 `workflow.json`에 남는다.

**대시보드:** 실제 데이터로만 수집·필터·검토·결재·결정 현황, AI 권고 분포, 결정 일치율, 결재 대기, 마감 임박 공고를 보여준다.

### 실제 데이터로 확인한 것

- **수집:** 2026-10-27 기준 최근 30일, 키워드 5개로 771건을 7초 만에 받았다(검토 대상 13 / 확인 필요 10 / 제외 748).
- **첨부:** 검토 대상 13건 중 12건은 RFP가 HWP라서, 주 흐름은 "공고문 자동 + RFP PDF 업로드"다.

### 최종 리뷰와 수정

별도 검토자의 결론은 "고친 뒤 마무리 가능"이었다(치명적 0건). 6건을 고쳤고, 각각 실패하는 테스트를 먼저 만든 뒤 통과시켰다.

| 지적 | 수정 |
|---|---|
| RFP 업로드 전에 화면을 떠나면 공고가 "RFP 업로드 대기"에 갇힘(실제 공고 대부분이 지나는 주 흐름) | 공고함에 "RFP 업로드 이어서" 버튼 추가, 실행 실패 뒤 "다시 시도"해도 공고 폴더 유지 |
| 이미 보고서가 있는 검토 건에도 업로드가 되어 결재 흐름을 우회 | 409로 거부하고 "다시 실행"을 쓰도록 안내 |
| 다시 실행이 실행 전에 상태를 바꿔, 실패하면 반려 요청이 사라짐 / 다시 실행한 방식(offline·live)이 잘못 표시 | 새 보고서가 생긴 뒤에만 "검토 완료"로 전이, 보고서별 실행 방식을 `<보고서>.run.json`에 기록 |
| 건너뛴 첨부, 이름 단서 없이 RFP로 추정한 PDF, 꺼진 시장조사를 알리지 않음 | 진행 화면과 업로드 화면에 안내 |
| 대시보드 "마감 임박"에 마감 지난 공고·이미 시작한 공고가 섞임 | 둘 다 빼고, 공고함 배지에서도 마감 지난 공고를 뺌 |
| 키 오류 응답(XML)이 "연결 실패"로 보임 | 실제 원인(예: `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`)을 보여줌 |

**미뤄 둔 작은 문제**
- API로는 같은 공고를 여러 번 시작할 수 있다(화면에서는 막음).
- 체크리스트 저장과 결재 올리기가 동시에 일어나는 드문 경합이 있다.
- 업로드 화면은 역할을 모른다. 본부장이 제출하면 서버가 403으로 막는다.
- 원본 RFP가 없으면 "다시 실행" 버튼이 이유 표시 없이 숨겨진다.
- CLI 결과 폴더 이름에 `#`·`?`가 있으면 진행 스트림 주소가 깨질 수 있다.
- 공고에서 시작할 때 시장조사 스위치가 없다(항상 꺼짐).
- 대시보드 "규칙 필터 통과" 설명에 담당자 포함분이 빠져 있다.

## 7. 판단 기준 세트 (2026-10-28)

설계: `docs/superpowers/specs/2026-10-28-criteria-sets-design.md` · 계획: `docs/superpowers/plans/2026-10-28-criteria-sets.md`

- **기본 세트:** `config/notice_filter.yaml`과 `config/checklist.yaml`을 그대로 쓴다. 화면에서 고치거나 지울 수 없다.
- **사용자 세트:** 판단 기준 화면에서 기본이나 다른 세트를 복제한 뒤, 이름을 붙이고 값을 고쳐 저장한다. 저장 위치는 `outputs/criteria/sets/<이름>.json`이다.
  - 고칠 수 있는 값: 금액 하한, 마감 경고 일수, 분야 키워드, 제외·확인 필요 계약방식, S2 키워드, S3 핵심 기관, Go·검토 점수 구간
  - 나머지 규칙과 항목 문구는 기본 세트를 따른다.
- **적용 세트:** 한 번에 하나만 쓰고, `outputs/criteria/active.json`에 저장한다. 본부장만 바꿀 수 있다. 적용 중인 세트는 지울 수 없다(409).
- **이미 판정한 건 고정:**
  - 공고: 수집할 때 `judged.criteria_set`에 세트 이름을 기록한다.
  - 검토 건: 실행을 시작할 때 체크리스트 설정을 건 폴더 `criteria.json`에 스냅샷한다. 시작에 실패하면 스냅샷은 그대로다.
  - 스냅샷이 없는 CLI·기존 건은 기본 세트로 평가한다.
- **화면 표시:** 공고함 정보 상자에 "적용 기준"을 보여 준다. 기본이 아닌 세트로 판정한 공고에는 "기준: 이름"을, 결과 화면 체크리스트 탭에는 "판단 기준: 이름"을 표시한다.
- **아이콘:** 대시보드는 위젯 배치(`IconDashboard.tsx`), 판단 기준은 저울(`IconCriteria.tsx`)이다. 둘 다 직접 그렸고 24px, 선 1.8px이다.
- **API:**
  - `GET /api/criteria?set=` (sets·active·selected·values 추가)
  - `PUT|DELETE /api/criteria/sets/{name}`
  - `PUT /api/criteria/active` (본부장)
- **테스트:** `tests/test_criteria.py`, `tests/test_app_criteria.py`, `web/src/criteria.test.ts`
- **미뤄 둔 문제:**
  - 공고함의 "적용 기준"은 다음 수집에 쓸 기준이다. 적용 세트를 바꾼 직후 화면에 남아 있는 공고는 이전 기준으로 판정한 결과다.
  - 세트 이름은 바꿀 수 없다. 복제해 새 이름으로 저장한 뒤 이전 세트를 지운다.

## 9. QA 반영 (2026-10-28)

- **좁은 화면**
  - 1100px 이하: KPI 2열, 2열 콘텐츠는 1열로 바꾼다.
  - 900px 이하: 사이드바는 아이콘만 남긴다. 메뉴 이름은 `title`과 `aria-label`로 둔다.
  - 640px 이하: 카드 그리드를 1열로 바꾼다.
- **키보드 조작**
  - 검토 목록·결재함·의사결정 이력·대시보드 마감 임박 표의 공고명을 실제 버튼(`.row-link`)으로 바꿨다. Tab으로 이동하고 Enter·Space로 연다.
  - 표는 가로 스크롤 래퍼(`table-scroll`)로 통일했다.
- **PDF 선택 영역:** Enter와 Space 모두 파일 선택을 연다. 형식 오류는 `role="alert"`로 화면 읽기 도구에 알린다.
- **불러오기 실패:** 대시보드·결재함·의사결정 이력·판단 기준 화면에 "다시 시도" 버튼(`components/LoadError.tsx`)을 둔다.
- **처리 흐름 단계 이름:** 원 숫자를 "1. 수집"처럼 일반 숫자로 바꿨다.
- **후속 반영 (2026-10-29)**
  1. **URL 라우팅:** `#/run/<id>`처럼 화면이 주소에 남는다(`web/src/route.ts`, 테스트 `route.test.ts`). 새로고침, 뒤로가기·앞으로가기, 링크 공유가 된다. 주소 없이 열면 실행 중인 검토의 진행 화면으로 간다.
  2. **공고함 검색·정렬:** 공고명·기관을 검색할 수 있다. 대소문자와 띄어쓰기는 무시한다. 정렬은 마감 임박순과 예산 큰 순이다(`findNotices`).
  3. **결과 화면 위계**
     - 결정할 수 있거나 이미 결정된 건은 결정 카드를 분석 탭 위로 올린다.
     - 요약 탭은 요약 → 다음 할 일(강조) → 핵심 발견 → 입찰 조건 순서다.
  4. **진행 로그:** 접힌 상태(`<details>`)로 시작하고, 실패하면 펼친다.
     - 서버는 켜져 있는데 해당 실행이 없으면 "진행 중인 실행이 아니에요"와 검토 목록 버튼을 보여 준다(`afterDisconnect` → `gone`).
  5. **목록 상태 공통화:** 빈 목록은 `components/Empty.tsx`, 불러오기 실패는 `LoadError`를 쓴다. 검토 목록도 실패하면 다시 시도할 수 있다(이전에는 로딩에서 멈췄다).

## 10. 검색·필터 · 전체 검토 시작 (2026-10-29)

- **검색·필터 (`web/src/filters.ts`, `components/FilterBar.tsx`)**
  - 공고함: 공고명·기관 검색, 마감(7일 이내 / 8~14일 / 15일 이후 / 마감일 없음), 예산 구간. 검색창이 정렬 버튼 앞까지 늘어난다.
  - 검토: 공고명·공고번호 검색, AI 권고, 결재 상태
  - 결재함: 공고명·공고번호 검색, AI 권고, 예산 구간
- **전체 검토 시작 (공고함 헤더)**
  - 검토 대상 중 아직 시작하지 않은 공고를 마감 순으로 서버가 한 건씩 차례로 실행한다(`POST /api/notices/start-all`, 담당자만).
  - 실행 방식은 offline·live 중에 고른다. live는 비용 경고를 보여 준다. 시장조사는 끈다.
  - RFP PDF가 없는 공고는 건너뛰고 "RFP 업로드 대기"로 남긴다.
  - 진행 상황은 `GET /api/notices/batch`로 본다. **중지**(`POST /api/notices/batch/stop`)를 누르면 지금 건이 끝난 뒤 멈춘다.
  - 끝나면 완료·업로드 대기·실패 건수와 이름을 보여 준다.
  - 일괄 실행 중에는 개별 검토 시작을 막는다(409).
  - 진행 상태는 서버 메모리에만 있어서 서버를 다시 켜면 사라진다. 이미 만든 보고서는 남는다.
- **테스트:** `tests/test_app_batch.py`, `web/src/filters.test.ts`
