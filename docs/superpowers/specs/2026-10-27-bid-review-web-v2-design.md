# 공공 SI 입찰 검토 웹페이지 v2 설계 — 공고 수집 · 대시보드 · 역할별 결재

작성일: 2026-10-27 · 선행 설계: `2026-10-27-bid-review-web-design.md`(v1, 구현 완료) · 근거 문서: 3·4·5주차 과제 PDF

## 1. 무엇을 왜 바꾸나

v1은 "PDF 한 건을 올려 검토하는 화면"이다. v2는 3주차 과제의 **To-Be 업무 흐름 전체**를 웹에서 돌린다.

| 단계 | 담당 | 내용 |
|---|---|---|
| ① 공고 수집 | Program | 나라장터 API로 공고 수집 |
| ② 규칙 필터 | Program | 금액·마감·분야 기준으로 거르기 |
| ②-1 HITL-2 | 사업기획 담당자 | 참가자격 확인 |
| ③ 문서 확보 | Program | 첨부파일 받기 |
| ④~⑦ | Agent 1~4 | 분석과 보고서 작성 |
| ⑧ HITL-1 | 사업본부장 | 검토·결정, 반려 |
| ⑨ 이력 저장 | Program | 결정 기록 |

사용자 요청 세 가지:
- 왼쪽 메뉴를 **큰 업무 단위**로 바꾼다.
- **대시보드**를 추가한다.
- HITL에서 역할이 다르므로 **역할마다 권한을 다르게** 준다.

사용 맥락은 v1과 같다. 팀 발표 때 화면에 띄워 실제로 시연하고, 프리세일즈 담당자가 실제로 쓸 수 있는 도구여야 한다.

승인된 시안: `.superpowers/brainstorm/71305-1793104972/content/layout-v2-dashboard.html` (대시보드, 공고함, 권한 표)

## 2. 목표 / 비목표 / 반목표

**목표**
- 공고함에서 "지금 수집"을 누르면 나라장터 용역 입찰공고를 가져오고, 규칙으로 **검토 대상 / 담당자 확인 필요 / 제외**로 나눈다.
- 검토 대상 공고에서 바로 Agent 검토를 시작한다. 첨부된 공고문·RFP PDF를 자동으로 받는다.
- 상단에서 역할(사업기획 담당자 / 사업본부장)을 바꾸면 메뉴 배지, 버튼, 서버 권한이 함께 바뀐다.
- 결재 흐름을 만든다. 담당자가 결재를 올리고, 본부장이 결정하거나 반려(사유 필수)하고, 반려되면 담당자가 보완해 다시 올린다.
- 대시보드는 **실제 데이터로만** 수집부터 결정까지 현황을 보여준다.
- v1의 기능(업로드 검토, 진행 표시, 결과 탭, 체크리스트, 다운로드)은 그대로 유지한다.

**비목표 (이번에 안 함)**
- 실제 로그인·계정·보안 인증. 역할 전환은 시연용이다(4.2).
- 자동 주기 수집(스케줄러). "지금 수집" 버튼으로만 가져온다.
- HWP/HWPX를 PDF로 변환. 첨부가 HWP뿐이면 담당자가 PDF를 올린다.
- Agent 하나만 다시 실행하기. 파이프라인 구조상 다시 실행하면 4개 Agent가 모두 돈다.
- 웹에서 판단 기준(YAML) 편집. 보기만 한다.

**반목표 (돌아가도 이렇게 되면 실패)**
- 화면에서는 버튼이 숨겨졌는데 API로는 다른 역할의 동작이 되는 것. 권한은 화면과 서버 **둘 다** 지킨다.
- 대시보드에 예시 숫자나 지어낸 숫자가 보이는 것. 데이터가 없으면 0이나 "아직 수집하지 않았어요"를 보여준다.
- AI 권고가 최종 결정처럼 보이는 것(v1과 동일).
- API 키가 화면·응답·로그·저장 파일에 노출되는 것(v1과 동일).
- 규칙 필터가 근거 없이 공고를 제외하는 것. 판단할 값이 없으면 "제외"가 아니라 "담당자 확인 필요"로 둔다.

## 3. 화면

### 3.1 공통 틀

- **상단 바:** 로고, 제목, 오른쪽에 역할 전환 segmented control `사업기획 담당자 | 사업본부장`.
- **왼쪽 메뉴:** 아래 6개. 숫자 배지는 실제 건수다.

| 메뉴 | 배지 |
|---|---|
| 대시보드 | — |
| 공고함 | 검토 대상 수 |
| 검토 | 진행 중 수 |
| 결재함 | 본부장: 결재 대기 수(빨강) / 담당자: 보완 요청 수 |
| 의사결정 이력 | — |
| 판단 기준 | — (구분선 아래) |

- v1의 "왼쪽 공고 목록"은 **검토** 메뉴 안으로 옮긴다.
- 디자인 시스템은 v1과 같다(Montage 4.1.3, Pretendard, 토큰 색).

### 3.2 대시보드

모든 수치는 **실제 데이터**로 계산한다.

- **카드 4장:**
  - 수집한 공고(최근 수집 기간·키워드 표시)
  - 규칙 필터 통과
  - 담당자 확인 필요
  - 결재 대기
- **처리 흐름 막대:** ① 수집 → ② 필터 통과 → Agent 검토(검토 건수) → ⑧ 결재 대기 → ⑨ 결정 완료
- **AI 권고 분포:** 검토된 보고서의 `decision_status`가 Go / 조건부 Go / 보류 / No-Go 각각 몇 건인지. AI 권고와 본부장 결정이 둘 다 있는 건의 일치율도 보여준다.
- **결재 대기 목록:** 공고, 예산, AI 권고, 체크리스트 권고. 본부장 역할일 때만 "결정" 버튼이 있고, 누르면 결정 화면으로 간다.
- **마감 임박 검토 대상:** 검토 대상 공고 중 마감이 가까운 순서. D-day를 보여준다.
- **수집 전 상태:** 수집한 적이 없으면 카드는 0으로 두고 "공고함에서 지금 수집을 눌러 주세요"라고 안내한다.

### 3.3 공고함 (① 수집 · ② 필터 · ②-1 HITL-2)

- **머리:** 기간 선택(최근 7일 / 30일, 기본 30일), 키워드(기본값은 YAML), "지금 수집" 버튼(담당자만).
  - 수집하는 동안 진행 표시를 보여준다.
  - 끝나면 수집 건수와 판정별 건수를 알린다.
- **탭 4개:**
  - 검토 대상
  - 담당자 확인 필요
  - 제외
  - 검토 중·완료 (검토를 시작한 공고)
- **표 열:**
  - 공고명, 발주기관, 계약방법
  - 예산 (배정예산, 없으면 추정가격)
  - 마감
  - 필터 판정 + 근거 문구
  - 첨부 (PDF n / HWP n)
  - 동작
  - 공고명을 누르면 나라장터 상세(`bidNtceDtlUrl`)가 새 탭으로 열린다.
- **동작 버튼 (담당자만):**
  - 검토 대상: "검토 시작"
  - 확인 필요: "포함" / "제외". 둘 다 사유 입력 필수(HITL-2). 포함하면 검토 대상으로, 제외하면 제외로 옮기고 사유를 남긴다.
  - 검토 중·완료: "보고서" 버튼으로 그 검토 결과를 연다.
- **역할 차이:** 본부장 역할에서는 동작 버튼을 숨기고 "담당자 권한" 표시만 둔다.

### 3.4 검토

- v1의 화면을 그대로 쓴다: 새 공고 검토(업로드), 진행 표시, 결과(카드·탭·체크리스트).
- 이 메뉴 안의 목록에 **v1 왼쪽 목록**(검토한 보고서, 진행 중)이 들어간다.
- 공고함에서 "검토 시작"을 누르면:
  1. ③ 첨부를 받는다(4.4).
  2. RFP PDF가 있으면 바로 실행하고 진행 화면으로 간다.
  3. 없으면 업로드 화면으로 간다. 이때 공고문 PDF는 미리 채워 두고, "RFP가 HWP뿐이라 PDF로 올려 주세요"라고 안내한다.
- **결과 화면에 추가할 것:**
  - 결재 상태 배지와 결재 이력(올림, 반려 사유, 결정)
  - 담당자: "결재 올리기"(검토 완료 상태일 때), "다시 실행"(보완 요청 상태일 때)
  - 본부장: v1의 "사업본부장 결정" 카드가 결재 대기 상태일 때만 동작하고, "반려" 버튼이 추가된다.
  - 체크리스트 수정은 담당자만, 그리고 결재 대기·결정 완료 상태가 아닐 때만 할 수 있다.

### 3.5 결재함

- **본부장:** "결재 대기" 목록. 공고, 예산, AI 권고, 체크리스트 권고, 올린 시각. 누르면 결과 화면에서 결정·반려한다.
- **담당자:** 두 목록.
  - "보완 요청": 반려된 건, 반려 사유, 요청 방식(재실행 / 수기 보완)
  - "내가 올린 결재 대기"

### 3.6 의사결정 이력

- 결정된 모든 건을 표로 보여준다: 결정일, 공고명, 예산, AI 권고, 체크리스트 권고, 본부장 결정, 사유, 반려 횟수.
- AI 권고와 결정이 다르면 표시한다.
- 위쪽에 결정별 건수(Go / 보류 / No-Go)를 보여준다.
- 3주차 PDF의 "의사결정 이력 축적"에 해당한다.

### 3.7 판단 기준 (보기 전용)

- 공고 필터 규칙(`config/notice_filter.yaml`)을 표로 보여준다.
- Go/No-Go 체크리스트(`config/checklist.yaml`)의 1단계·2단계 항목과 점수 구간을 보여준다.
- 근거 데이터 요약을 보여준다(3년 낙찰 93건, `data/market/itcen_group_awards_3y.json`의 meta).
- "YAML을 고쳐 바꾼다"는 안내와 파일 경로를 적는다.

## 4. 정해진 동작

### 4.1 역할별 권한 (사용자가 시안으로 승인)

| 동작 | 담당자 | 본부장 |
|---|---|---|
| 공고 수집, 확인 필요 공고 포함·제외 (HITL-2) | ✅ | 보기만 |
| 검토 시작, 업로드, 다시 실행 | ✅ | 보기만 |
| 체크리스트 수정 | ✅ | 보기만 |
| 결재 올리기 | ✅ | — |
| 최종 결정 Go / 보류 / No-Go, 반려 (HITL-1) | — | ✅ |
| 대시보드, 이력, 판단 기준, 결과·다운로드 보기 | ✅ | ✅ |

### 4.2 역할 전환 (사용자 결정: 로그인 없이 상단에서 전환)

- 고른 역할은 브라우저 `localStorage`에 기억한다. 첫 방문 기본값은 담당자다.
- 상태를 바꾸는 API 요청에는 헤더 `X-Role: staff | director`를 붙인다.
- 서버는 4.1 표에 따라 맞지 않으면 403을 돌려준다. 오류 문구 예: "사업본부장만 결정할 수 있습니다".
- 이것은 **시연용 역할 구분이지 보안이 아니다.** 같은 PC의 누구든 역할을 바꿀 수 있다. 문서와 판단 기준 화면에 이 점을 적는다.
- 기록되는 이력(결재·결정·포함/제외)에는 역할 이름을 함께 남긴다.

### 4.3 공고 수집과 규칙 필터 (Claude의 결정, 금액 하한은 사용자 결정)

**수집 API**
- 조달청 나라장터 입찰공고정보서비스 `https://apis.data.go.kr/1230000/ad/BidPublicInfoService/getBidPblancListInfoServcPPSSrch` (용역)
  - `inqryDiv=1`(공고게시일시), `bidNtceNm=<키워드>`, `numOfRows=999`
  - 키워드마다 호출하고 페이지를 넘긴다.
  - 30일을 한 번에 조회하는 것이 동작함을 확인했다. 더 긴 기간은 v1처럼 31일 단위로 나눈다.
- **키:** `.env`의 `G2B_BID_NOTICE_KEY`를 쓰고, 없으면 `G2B_SERVICE_KEY`를 쓴다. 키가 없으면 "지금 수집"을 비활성화하고 이유를 보여준다.
- **중복:** `bidNtceNo + bidNtceOrd`로 합친다. 같은 공고의 새 차수(정정공고)는 별도 공고로 둔다.
- **저장:** `outputs/notices/notices.json`. 공고 원본 필드 중 화면·필터에 쓰는 것만 저장하고, 판정 결과와 HITL-2 기록을 함께 둔다. 다시 수집하면 HITL-2 기록과 검토 연결은 유지한다.

**필터 규칙** (새 파일 `config/notice_filter.yaml`, 값은 모두 YAML)

| 규칙 | 검토 대상 | 제외 | 담당자 확인 필요 |
|---|---|---|---|
| 금액: `asignBdgtAmt`, 없으면 `presmptPrce` | ≥ **40억** | < 40억 | 둘 다 없음 |
| 마감: `bidClseDt` | 지금보다 `deadline_warn_days`(기본 3일) 넘게 남음 | 이미 지남 | 비어 있음, 또는 3일 이내 |
| 분야: `pubPrcrmntLrgClsfcNm` 또는 공고명 키워드 | "ICT 서비스"이거나 키워드 일치 | 둘 다 아님 | — |
| 계약방법: `cntrctCnclsMthdNm`, `sucsfbidMthdNm` | 그 밖 | `수의계약` 포함 | — |
| 참가 조건: `cntrctCnclsMthdNm`이 `제한경쟁`, 또는 `indstrytyLmtYn=Y`, 또는 지역제한 값(`rgnLmtBidLocplcJdgmBssNm`)이 있음 | 해당 없음 | — | 해당 있음 (공고문 원문 확인) |

- **판정 합치기:** 공고마다 규칙별 판정을 모두 남기고, 최종 판정은 **제외 > 확인 필요 > 검토 대상** 순으로 가장 강한 것을 따른다.
- **근거 문구:** 사유는 사람이 읽을 수 있게 남긴다. 예: "40억 미만(0.4억)", "마감일 없음".
- **필드 값 주의:** 실제 응답에서 `rgnLmtBidLocplcJdgmBssNm`은 지역제한이 없어도 "본사또는참여지사소재지" 같은 값이 올 수 있다. 지역제한 여부를 어떤 필드로 판정할지는 구현자가 실제 응답 여러 건으로 확인해 정하고, 그 결정을 YAML 주석에 남긴다(5장).

### 4.4 문서 확보 (③)

- `ntceSpecFileNm1~10`과 `ntceSpecDocUrl1~10`에서 **PDF만** 받는다. 로그인 없이 받아지는 것을 확인했다.
- **파일 분류:**
  - 이름에 `공고문` 또는 `입찰공고`가 있으면 공고문 → `notice.pdf`
  - 그 밖의 PDF 중 이름에 `제안요청`, `과업`, `RFP`가 있는 것을 우선으로 RFP → `rfp.pdf`
  - 그런 이름이 없으면 공고문이 아닌 첫 PDF를 RFP로 쓴다.
- **저장 위치:** v1과 같은 `outputs/web/<실행시각>/`. `upload.json`에 `notice_id`(공고번호·차수)와 원래 파일명을 남긴다.
- **실행:** 공고문 PDF가 있으면 `--notice-pdf`로 넘긴다. 실행 방식(offline/live)은 "검토 시작" 때 v1 업로드 화면과 같은 선택지로 고른다. 나라장터 시장조사 스위치 규칙은 v1과 같다.
- **실패 처리:** 다운로드 실패나 PDF 검사 실패(`%PDF-` 아님) 때는 그 파일을 건너뛰고 화면에 알린다. RFP PDF가 하나도 없으면 업로드 화면으로 간다(3.4).

### 4.5 결재 흐름 (Claude의 결정 — 3주차 PDF HITL-1 "반려 사유 입력 → 해당 Agent 재실행 또는 담당자 수기 보완"을 반영)

검토 건마다 상태를 둔다. 저장은 건 폴더의 `workflow.json`이다(4.7).

```
검토 완료 ──[담당자: 결재 올리기]──▶ 결재 대기 ──[본부장: 결정]──▶ 결정 완료
                                        │
                                        └─[본부장: 반려(사유 필수, 요청: 재실행|수기 보완)]─▶ 보완 요청
보완 요청 ──[담당자: 체크리스트 수정 후 결재 올리기]──▶ 결재 대기
보완 요청 ──[담당자: 다시 실행]──▶ 같은 폴더에 새 보고서 → 건 상태는 검토 완료, 이력은 이어짐
```

- **기본 상태:** `workflow.json`이 없는 건(기존 CLI 결과 포함)은 "검토 완료"로 본다. 결재는 언제나 그 건의 현재 보고서를 대상으로 하며, 옛 보고서 화면에서는 결재 버튼을 보이지 않는다.
- **이력:** 모든 전이를 `history`에 남긴다: `{from, to, role, at(KST), reason?, request?}`.
- **결정 저장:** 본부장 결정은 v1의 `<보고서>.decision.json`에 그대로 저장한다. 결정 완료 뒤에도 본부장은 v1처럼 결정을 바꿀 수 있고, 이전 값은 `decision_history`에 쌓인다.
- **허용되지 않는 전이:** 409와 함께 현재 상태를 알려준다. 예: 결재 대기가 아닌데 결정하려는 경우.
- **다시 실행:** 그 보고서의 원래 입력(`rfp.pdf`, `notice.pdf`, `upload.json`의 mode)으로 같은 폴더에서 다시 실행한다. CLI 결과(웹 업로드가 아닌 것)는 원래 PDF를 `data/input`에서 찾는다(v1의 `_find_pdf` 규칙). 못 찾으면 다시 실행을 비활성화한다.

### 4.6 API (v1에 추가)

| 메서드·경로 | 권한 | 하는 일 |
|---|---|---|
| `POST /api/notices/collect` body `{days, keywords}` | 담당자 | 수집과 필터를 실행하고 요약을 돌려준다. 동시에 하나만 실행하며, 실행 중이면 409 |
| `GET /api/notices?verdict=` | 모두 | 목록. 판정, 근거, 첨부 요약, 연결된 run_id를 포함 |
| `PUT /api/notices/{id}/review` body `{include: bool, reason}` | 담당자 | HITL-2 포함·제외 |
| `POST /api/notices/{id}/start` body `{mode, market_api}` | 담당자 | 첨부를 받고 실행한다. `{job_id}` 또는 `{needs_upload: true, folder_id, notice_pdf: bool}`을 돌려준다(4.8) |
| `GET /api/dashboard` | 모두 | 3.2의 모든 수치 |
| `PUT /api/runs/{id}/workflow` body `{action: submit\|reject\|resubmit, reason?, request?}` | 행동별(4.1) | 결재 상태 전이 |
| `POST /api/runs/{id}/rerun` body `{mode, market_api}` | 담당자 | 다시 실행. `{job_id}`를 돌려준다(4.8) |
| `GET /api/approvals` | 모두 | 역할별 결재함 목록 |
| `GET /api/decisions` | 모두 | 의사결정 이력 |
| `GET /api/criteria` | 모두 | 필터 규칙, 체크리스트, 근거 데이터 요약 |

- v1 API 중 상태를 바꾸는 것(`POST /api/runs`, `PUT checklist`, `PUT decision`)에도 4.1 권한 검사를 더한다.
- `PUT decision`은 결재 대기(또는 결정 완료 상태의 변경)일 때만 허용한다.

### 4.7 검토 건(case)과 집계 단위 (Claude의 결정)

**검토 건 = 보고서 폴더 하나**
- 웹 실행 폴더, CLI 폴더(`outputs/offline/001_…` 등) 모두 폴더 하나가 검토 건 하나다.
- 그 폴더의 **가장 최근 보고서**가 그 건의 현재 보고서다. 다시 실행하면 같은 폴더에 새 보고서가 생기고, 그것이 현재 보고서가 된다.

**결재 상태는 보고서가 아니라 건 단위로 저장한다**
- 4.5의 `<보고서>.workflow.json` 대신 폴더의 `workflow.json`에 둔다.
- 그래서 다시 실행해도 결재 이력과 반려 횟수가 이어진다.
- `history`의 각 항목에는 그때의 보고서 이름(`report`)을 남긴다.
- 체크리스트 수정값과 결정은 v1처럼 보고서별 파일에 둔다. 새 보고서는 새 분석이므로 수정값을 이어받지 않는다.
- 옛 보고서는 v1처럼 보기만 할 수 있다.

**집계 단위**

| 항목 | 셈하는 대상 |
|---|---|
| 처리 흐름 막대(① 수집 → ② 필터 → 검토 → 결재 → 결정) | **공고에 연결된 건만** |
| 수집 전 상태 | 막대와 공고 카드는 0 |
| AI 권고 분포 | 모든 건의 현재 보고서 (CLI·업로드 포함, 실제 검토 결과라서) |
| 결재 대기, 일치율, 의사결정 이력 | 모든 건의 현재 보고서 |
| 별도 카드 | "전체 검토 n건 (공고 연결 m건)"으로 차이를 드러냄 |

### 4.8 수집 결과 누적 · 분야 규칙 · 다시 실행 세부 (Claude의 결정)

**공고 저장은 누적한다**
- 다시 수집하면 `notices.json`에 합친다. 이미 있는 공고는 원본 필드와 판정을 새로 고친다.
- HITL-2 기록과 검토 연결은 유지한다.
- 이번 수집 범위 밖이 된 공고도 지우지 않는다.
- 대시보드 "수집한 공고" 카드에는 "최근 수집 n건 · 누적 m건"과 최근 수집 시각·조건을 보여준다.

**분야 규칙과 수집 키워드는 분리한다**
- 수집 키워드(`collect_keywords`)는 검색어일 뿐이다.
- 분야 규칙은 조달 분류(`pubPrcrmntLrgClsfcNm`)가 YAML의 `ict_classes`(기본 "ICT 서비스")에 들어 있는지로 판정한다.
- 분류 값이 비어 있을 때만 공고명이 `field_keywords`(기본값은 수집 키워드와 같음)에 걸리는지로 대신 판정한다.
- 이렇게 해야 키워드로 검색됐지만 ICT가 아닌 공고(예: "정보시스템" 이름이 붙은 시설 공사 용역)가 걸러진다.

**다시 실행**
- 누를 때마다 실행 방식(offline/live)을 다시 고른다. 기본값은 **offline**이다.
- live를 고르면 v1처럼 비용 안내를 보여준다.
- CLI 결과처럼 `upload.json`이 없는 건은 공고문 없이 RFP만으로 다시 실행한다.
- 원본 RFP를 찾을 수 없으면 다시 실행을 비활성화한다.

**공고에서 시작했는데 RFP PDF가 없을 때**
- `POST /api/notices/{id}/start`가 먼저 실행 폴더를 만들고 `notice.pdf`(있으면)와 `upload.json`(`notice_id` 포함)을 저장한다. 그다음 `{needs_upload: true, folder_id}`를 돌려준다.
- 업로드 화면은 `POST /api/runs`에 선택 필드 `folder_id`를 함께 보낸다.
- 서버는 `folder_id`가 있으면 새 폴더를 만들지 않고 그 폴더에 `rfp.pdf`를 저장해 실행한다. 이미 있는 `notice.pdf`는 `--notice-pdf`로 넘긴다.
- `folder_id`는 `outputs/web/` 아래의 기존 폴더 이름만 허용한다.

## 5. 남겨 둔 것 (구현자가 정함)

- 지역제한·업종제한 판정에 쓸 정확한 필드와 값. 실제 응답 여러 건으로 정하고 YAML 주석에 근거를 적는다.
- 공고 저장 파일에 남길 필드 목록과 화면 정렬·검색 방식.
- 대시보드 막대와 분포의 시각 표현(CSS로 충분, 차트 라이브러리는 쓰지 않음).
- 결과 화면 안에서 결재 카드를 어디에 둘지(단, 본부장 결정은 v1 결정 카드 자리를 쓴다).
- 공고함 수집 진행 표시를 SSE로 할지, 요청 하나로 기다릴지. 수집은 수십 초 이내로 끝난다.

## 6. 확인 방법

- **백엔드 테스트(기존 assert 스크립트 방식):**
  - 필터 규칙: 금액 경계 40억, 금액 없음, 마감 지남·임박·없음, 수의계약, 제한경쟁·업종제한, 판정 우선순위
  - 첨부 분류: 공고문 / RFP / HWP만 있음
  - 수집 결과 합치기: 중복, 재수집 시 HITL-2 기록 유지
  - 결재 상태 전이: 허용·거부, 이력
  - 역할 권한: 엔드포인트마다 잘못된 역할이면 403
  - 대시보드 수치를 작은 고정 데이터로 계산
- **실제 API 확인:** 수집은 실제 API로 한 번 돌려 건수와 판정 분포를 확인한다(키 필요). 테스트는 가짜 응답을 쓴다.
- **브라우저 시연:**
  1. 담당자: 수집 → 확인 필요 1건 포함(사유) → 검토 시작(첨부 자동, offline) → 결과 → 결재 올리기
  2. 본부장으로 전환: 결재함 → 반려(사유, 수기 보완)
  3. 담당자: 보완 요청 → 체크리스트 수정 → 다시 결재 올리기
  4. 본부장: 결정 → 의사결정 이력, 대시보드 수치 확인
  5. 본부장 역할에서 담당자 버튼이 숨겨지는지, API를 직접 불러도 403이 나는지 확인
- 기존 테스트(v1 7개 파일, 프론트 9개)와 offline 회귀가 계속 통과해야 한다.
